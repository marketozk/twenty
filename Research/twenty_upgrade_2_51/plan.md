# Обновление демо Twenty до 2.51.0

26.10.2026. Пользователь прямо разрешил установить самую свежую версию.

Последний стабильный release API GitHub: `twenty/v2.51.0`, опубликован 25.10.2026. 2.52.0 в main — версия разработки. Источники: [release](https://github.com/twentyhq/twenty/releases/tag/twenty/v2.51.0), [upgrade guide](https://docs.twenty.com/developers/self-host/capabilities/upgrade-guide).

Цель: только Compose `twenty-demo` в `/opt/twenty-demo`. Краткая остановка server/worker; PostgreSQL16 и Redis7.4 остаются на месте. Порт 2020, настройки, секреты, пользовательские приложения и существующие данные сохраняются. Робот, SaleBot и другие контейнеры не входят в выкат.

## Preflight

- Server/worker: `twentycrm/twenty:v2.50.0`, одинаковый image ID; server healthy.
- `upgrade:status`: 2.50.0, instance up to date, 1 workspace up to date, 0 behind/failed.
- Compose на сервере совпадает с полным исходным файлом из предыдущего проекта; SHA256 `17497f2922b727dce61974293a51951072272f52227566dfd48774555448cb8a`.
- Environment 0600; изменяется только TAG после резервного копирования, без замены секретов шаблоном.
- Образ 2.51.0 заранее скачан. Свободно более 1 TiB; база около 22 MiB, local storage около 31 MiB.
- В релизе есть переход rich text BlockNote→TipTap. Команда зарегистрирована в upgrade runner; дополнительно вызывается документированная идемпотентная `upgrade:2-51:migrate-rich-text-to-tiptap`. Старое BlockNote-содержимое сохраняется самой командой.
- Entrypoint способен продолжить запуск после ошибки upgrade: одной зелёной healthcheck недостаточно. Обязательно проверить `upgrade:status`, конвертацию rich text и записи.
- Billing не включён через Compose, в database config нет переопределений, default `IS_BILLING_ENABLED=false`. Изменение формата BILLING_PLANS не требует включать облачный billing для этого демо.

## Выполнение

`upgrade.py` запускается целиком из зафиксированной Git-версии после SHA256-сверки. Lock и проверки исходного состояния предотвращают случайный повтор после обновления.

1. Остановить только server/worker.
2. Зафиксировать counts и множества ID основных CRM-таблиц.
3. Сохранить custom-format PG dump, файлы local storage, Redis RDB, полный текущий Compose/environment. Каталог backup 0700; новые файлы 0600. Проверить чтение dump/tar и сохранить hashes.
4. Атомарно заменить TAG, проверить Compose; поднять server 2.51 без изменения зависимостей.
5. Дождаться health; проверить/завершить rich text, проверить instance/workspace upgrade status и сохранность записей.
6. Поднять worker 2.51; проверить HTTP, контейнеры и открытие CRM. Выполнить отдельную проверку нового worker и заметок после скрипта.

Логи и данные backup остаются на сервере и не попадают в Git. Репозиторий содержит только обезличенный итог.

## Откат

До изменения TAG ошибка возобновляет старые server/worker. После начала миграций автоматический возврат только тега запрещён: старая версия может быть несовместима с новой схемой. При необходимости остановить оба приложения, сохранить диагностику, восстановить прежний `.env`, БД из `twenty.dump`, local storage и Redis RDB из одного согласованного backup; затем поднять оба приложения 2.50 и проверить данные/upgrade status. Старый образ и backup не удаляются. Откат выполняется только после выяснения причины, без слепого повторения миграции.
