## M-7, остаток R1 (governed→ordinary во время publish)

**Что добавлено:** `design/09-automation-contract.md:124` и такой же абзац в `plan/implementation-spec.md:541`.

| Направление гонки между commit события и listener | Что гарантирует новый контракт | Итог |
|---|---|---|
| governed v1 → ordinary v2 (мой контрпример) | Listener пропускает workflowId, если он есть в неизменяемом плане этого события или был governed в снимке каталога на момент commit, даже когда сейчас активна ordinary v2. Остаётся один запуск, по закреплённой v1 | Двойного исполнения нет, контрпример снят |
| ordinary v1 → governed v2 | Listener никогда не запускает текущую governed-версию без заранее записанного intent. Для v1 сохранён пустой результат (empty outcome) | Не больше одного исполнения, событие не теряется без следа |
| Нет ссылки на событие или снимок | Видимый gap либо отказ для затронутой раздачи, без отката к кешу | Совпадает с «Cache не oracle» в `:120` |

**Почему этого достаточно:**
- Ссылка передаётся из транзакции мутации отдельно для каждой записи, в том числе внутри batch.
- Пользовательский payload её задать не может, а listener сверяет привязку к workspace и событию плюс неизменяемый hash источника.
- Отдельно оговорено, что это планируемое расширение внутренних типов, а не уже существующее поле WorkspaceEventBatch. То есть план не опирается на выдуманное поле. Это совпадает с тем, что я видел в исходниках в стадии A: listener читает кеш `workflowAutomatedTriggerMaps`.
- Тест T14-E теперь покрывает оба направления publish. Его оракул: не больше одного исполнения workflowId на исходное событие.

**Противоречий нет.** Старая фраза `design/09:120` («исключает по durable marker конкретной версии») новому правилу не противоречит, правило `:124` лишь расширяет её («Также…»). Вместе они согласуются с `spec:499`: второй постановки в очередь для governed target нет.
