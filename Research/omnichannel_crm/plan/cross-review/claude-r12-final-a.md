## Находки

### F1 — Medium: три разные формулы runId для message-root
- **Где:** spec §15.10, стр. 403 («stable workflowRunId = UUIDv5(workspaceId,eventId,workflowId)») и design/09, стр. 53 и 59. Против них: spec §3, стр. 77 и phase_5, стр. 42 — conversation.created и message.received одного root дают **один** intent через TargetClaim. А design/09, стр. 81 вводит третью формулу: runId по workspace + отсортированный набор roots + workflowId.
- **Сценарий:** одно живое сообщение порождает E1 (conversation.created) и E2 (message.received), оба нацелены на workflow W. Intent один, а формула eventId даёт два разных runId. Recovery по правилу «до runner ищется stable runId» (spec §15.17, стр. 481) пересчитает ID из receipt E1 и не найдёт run, созданный по E2. Дальше возможна ложная классификация gap/stalled либо попытка создать run. TargetClaim UNIQUE спасает от второго run, но реализации будут расходиться.
- **Минимальная правка:** одна формула для всех roots, например `UUIDv5(workspaceId, sorted(rootKind,rootId)…, coreWorkflowId)`, где для сообщения rootKind=admission. ConsumerReceipt хранит `runIntentId`, и recovery читает его через TargetClaim, не пересчитывая из eventId. Убрать формулу с eventId из §15.10 и design/09 §3.

### F2 — Medium: отзыв нативной роли не связан с policy epoch через кэш прав
- **Где:** spec §7, стр. 148 и §15.5, стр. 328 требуют, чтобы отзыв нативной роли шёл через тот же fence/epoch и чтобы чтения проверяли актуальный epoch. В коде нативные права (`rolesPermissions`, `userWorkspaceRoleMap`, `apiKeyRoleMap`, `roleIdsWithAllRecordsAccess`) загружаются из `WorkspaceCacheService.getOrRecompute` ещё до транзакции (`workspace-orm.manager.ts:154–167`) и передаются в `WorkspaceDataSource` (`workspace-data-source.service.ts:98–105`). В плане этот кэш нигде не упомянут.
- **Сценарий:** отзыв роли закоммитил epoch E+1. Запрос с контекстом, загруженным раньше (или во время запаздывающего пересчёта кэша), берёт FOR SHARE уже на E+1, но фильтрует по старой нативной разрешающей роли. Получается утечка после коммита отзыва, хотя оракул T10/T31 требует обратного.
- **Минимальная правка:** нормативно указать, что для защищённого контекста нативные входы ролей:
  - либо читаются из primary внутри fenced-транзакции;
  - либо берутся из кэша с меткой policyEpoch, которая сверяется после блокировки (несовпадение → пересчёт).

  Писатели нативных ролей повышают epoch в той же транзакции, что и запись в БД. Отрицательный контроль для T31: устаревший кэш.

### F3 — Low: FIFO и ручная замена команды (`replacesCommandId`) не согласованы
- **Где:** spec §4, стр. 110, design/06, стр. 88, decision-tables C17. Правило «B ждёт доказанного accepted/reject для A» сформулировано без исключений. Но для replacement C обещан «неопределённый порядок», и не сказано, обходит ли C предшественника A и что тогда с B, стоящей между ними.
- **Минимальная правка:** явно задать один вариант. Например: replacement переводит A в `ordering_released` с аудитом и предупреждением, после чего освобождаются все последователи по порядку `outboundSequence`, а исход A не меняется. Либо: C тоже ждёт A, и тогда UI так и объясняет.

### F4 — Medium: нет выбора по параллельным ответам двух менеджеров
- **Где:** requirements F-02, стр. 50; design/02, стр. 50 («явное подтверждение отправки на устаревшем состоянии»); design/04, стр. 23 («conflict/уведомление по revision»). Против этого: spec §8, стр. 164 и §15.19, стр. 522 — отправки не проверяют revision и не меняют controlEpoch.
- **Сценарий:** два менеджера одновременно отвечают на одно сообщение. Оба ответа уходят без предупреждения. Тест T12 по spec пройдёт, по design/04 — нет.
- **Минимальная правка:** либо добавить в `sendConversationMessage` необязательный `observedSequence` (не входит в hash, как и `expectedControlEpoch`) с ответом `stale_view`, требующим подтверждения; либо записать продуктовое решение «без предупреждения» и поправить design/02 и design/04 вместе с T12.

### F5 — Low: не определено значение `effectKind` в AutomationAdmission
- **Где:** spec §3, стр. 57; design/05, стр. 31. Значения нигде не перечислены, а UNIQUE включает это поле.
- **Риск:** если реализовать effectKind на каждого потребителя (ai, workflow), у одного сообщения появятся несколько admission и, значит, несколько roots и бюджетов. Это обход общей квоты (E01, design/09 §4).
- **Правка:** в v1 один `effectKind=customer_inbound`; новые виды не создают отдельного reply budget.

### F6 — Low: не задан режим блокировки WorkspacePolicyState для mode/takeover/close/status
- **Где:** decision-tables P05 («policy writes под UPDATE»), P06 и P12 (условно) против перечня в spec §15.15, стр. 463 и каталога §15.23, стр. 568, где mode и status отсутствуют.
- **Почему важно:** от этого зависят авто-переоткрытие по G20 внутри ingestion-транзакции, взятой в SHARE (§15.22, стр. 559), и takeover_on_send.
- **Правка:** явно указать SHARE или UPDATE для каждого из этих событий. Если UPDATE — ingestion заранее выбирает UPDATE, когда диалог закрыт и G20 включён.

### F7 — Low: не задан порядок показа ленты
- **Где:** sequence выдаётся при применении события (spec §3, стр. 49; §8, стр. 162/166). Импорт истории после live-сообщений получит более поздние sequence.
- **Правка:** sequence использовать только для курсора и доставки, а показывать по `sourcePosition`/`occurredAt` с детерминированным tiebreak. Добавить случай в T16.

## Явные риски (не дефекты плана)

- **Одна строка WorkspacePolicyState на workspace.** На ней сериализуются все защищённые чтения (FOR SHARE) и все policy-записи, включая каждый перенос стадии сделки. Риск признан: ранний gate T19 в ROB-766 с правилом «остановить расширение». Если gate не пройдёт, потребуется перепроектирование протокола.
- **Неразрешённый outcome_unknown человеческой команды навсегда блокирует auto в диалоге** (decision-tables, стр. 86). Обход без доказательства прямо запрещён. Это осознанное продуктовое следствие, но в реестре G его нет; стоит, чтобы владелец явно его принял.
- **Продуктовые настройки.** Без G01–G20 активация закрыта. Это не мешает начать ROB-764 с синтетическими fixtures.

## Итог по вердикту

Все критичные области просмотрены по документам, ключевые факты исходников сверены выборочно. Внешние коннекторы и юзерботы проверены только по вторичному описанию.

После правки F1, F2 и F4 и уточнения F3, F5, F6, F7 план, на мой взгляд, готов к реализации с указанными тестами и gates. ROB-764 почти не задет: F1 касается сущностей ROB-769, F2 — ROB-766, F4 — ROB-768.

Это оценка готовности к началу реализации. Она не означает production-готовность и не подтверждает, что runtime что-то выполнил: нового runtime пока нет.
