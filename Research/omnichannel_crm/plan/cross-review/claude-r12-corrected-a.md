## 2. Замечания

### M1 (Medium). Не определено, кто держит сессию юзербота и как старый отправитель отсекается на уровне юзербота

**Где:** `implementation-spec.md:235`, `:237`, `:363`, `:372`, `:378`, G13 `:259`; `research-connectors.md:28,54,114,126`.

**Сценарий.**
- §15.7 требует, чтобы юзербот сам проверял владельца и поколение (generation) и хранил tombstone отмены: «центральный CAS без этого недостаточен».
- При этом сейчас тех же юзерботов вызывают старый коннектор C (по HTTP, без поля generation), Mavibot и внешний MAX-API робота.
- В плане нет выбора между двумя вариантами:
  - (а) обновить живой юзербот на месте до версии с проверкой поколения — это затрагивает путь SaleBot;
  - (б) поднять новый процесс юзербота с новой сессией — тогда нужен новый вход, а одну Telegram-сессию нельзя держать в двух процессах.
- Не определено, как в журнале юзербота представлен «старый владелец», чьи команды приходят без поколения.

**Последствие.** Требование «доказать одного отправителя» (§15.24) нельзя реализовать однозначно. После переключения поколения старый C может продолжить отправлять через тот же юзербот. При откате журнал с доказательствами отправок может разойтись по разным процессам.

**Минимальное исправление** (§15.7 и §12):
1. Ровно один процесс-владелец сессии на аккаунт; сессии не копируются и не дублируются.
2. До переключения в юзербот выкатывается проверка поколения с явным legacy-владельцем generation 0 для вызовов C. Переключение — CAS в журнале юзербота; после него вызовы без текущего поколения отклоняются.
3. Откат выполняется симметрично, журнал остаётся тем же.
4. Mavibot и API робота классифицируются по §15.24.
5. В T11/T18 добавить проверку «отправка старого C после переключения отклонена юзерботом».

### L1 (Low). Резюме диалога и ИИ по запросу менеджера не покрыты

**Где:** `requirements.md:64` (F-04: «резюме диалога», «помощь в формулировке»); `implementation-spec.md:178` («human не запускает AI»).

**Сценарий.** Менеджер в режиме human хочет получить резюме или переформулировку. Текущая формулировка это либо запрещает, либо оставляет неописанным: не определены principal (менеджер ∩ агент), scope артефакта и запрет создания Command.

**Исправление.** Уточнить, что human запрещает только автономный запуск. Вызов по запросу менеджера — класс assist: пересечение прав менеджера и агента, артефакт под AutomationArtifactScope, без Command и без reply slot. Добавить в T25/T12.

### L2 (Low). Два разных ключа StageRule

**Где:** `implementation-spec.md:65` — UNIQUE(…,fromValue,toValue,…); `:326` — ключ (…,fieldMetadataId,optionValue).

**Исправление.** Одна схема: для read/edit используется optionValue, для transition — from/to, с явным wildcard-токеном. Тест T30 должен проверять оба вида.

### L3 (Low). Не определено, как коннектор использует `outboundSequence` после restore

**Где:** `design/06-api.md:88`; `implementation-spec.md:110`, `:318-320`.

**Сценарий.** После restore `nextOutboundSequence` откатывается назад. Если коннектор считает `outboundSequence` уникальным или обязательно растущим, новые команды конфликтуют с потерянными (orphan) командами в журнале.

**Исправление.** Явно записать: порядок обработки в коннекторе — порядок durable enqueue; `outboundSequence` — диагностическое поле. Либо restore обязательно повышает поколение, и последовательность действует в пределах поколения. Добавить в T29.

### L4 (Low). Текст удалённого сообщения остаётся в служебных копиях

**Где:** `implementation-spec.md:47` (`validatedEnvelope`), `:365` (`captured_events.originalPayload`), `:192`, `:284` (manifest purge перечисляет только Message/links/files/revisions).

**Сценарий.** После tombstone или controlled purge текст продолжает лежать в IncomingReceipt, в payload OutgoingCommand и в журнале коннектора.

**Исправление.** Включить эти хранилища в retention/purge manifest G10. Явно запретить их чтение путями поиска и ИИ.

### L5 (Low, редакционное). Старые схематичные ключи расходятся со spec

**Где:** `design/02-behavior.md:70`, `design/05-models.md:29,31` — admission по `nativeMessageKey`, MessageLink без conversationId. `integration-map.md:18` — «instance command в текущем 2-52», что противоречит §15.5.

Заголовки этих файлов объявляют spec приоритетным, поэтому реализацию это не блокирует. Но разработчик может взять неверный ключ — лучше удалить или пометить эти строки.

## 3. Остаточные риски (не дефекты плана)

- **Конкуренция за строку WorkspacePolicyState.** Каждое защищённое чтение и каждый ingress берёт её FOR SHARE на primary; назначения, связи и смена этапов берут FOR UPDATE. Это заметно меняет путь чтения: сейчас generic-чтение идёт в replica (`common-base-query-runner.service.ts:375`). Риск закрыт gate T19 с правилом остановки. Возможная оптимизация: согласованное чтение в одном снимке без блокировки строки — решать только после T19.
- **Бессрочный блок auto.** Неразрешённый человеческий `outcome_unknown` блокирует включение auto без срока (`decision-tables.md:86`). Это сознательное fail-closed решение, но владельцу продукта стоит знать: для MAX без поиска статуса блок может остаться навсегда.
- **Аудит после restore.** Аудит-записи, сделанные после снимка, при restore теряются; внешней копии нет. План это не скрывает.
