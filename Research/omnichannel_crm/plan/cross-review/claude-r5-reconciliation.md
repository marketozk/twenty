## Конкретный остаток

### N-13 (major): чего не хватает, кроме inventory
§15.13:398–400 уже требует manifest всех прямых и транзитивных импортов и DI, независимый baseline, fail-closed G18 и T20 с провайдерами, которые бросают исключение. **Сам полный перечень файлов — работа реализации, а не дефект плана.** В плане не хватает двух вещей.

1. **Архитектурного решения для функций с пометкой Enterprise, которые не относятся к ACL.** Уже по прочитанному коду, а не по будущему manifest, они стоят в общем runtime:
   - `RecordAccessPolicyService` фильтрует события SSE, webhook и logic function для всех объектов (`object-record-event-publisher.ts:34-54`, `call-webhook-jobs.job.ts:20-21`, `call-database-event-trigger-jobs.job.ts:26`);
   - на каждой записи проверяются validation rules и RLS (`workspace-repository.ts:74-76`);
   - `ShareWithService` вызывается в create-many (`common-create-many-query-runner.service.ts:50-54`);
   - есть record shares у запусков workflow и чатов агента;
   - `core-engine.module.ts:75-76` регистрирует модули RLS и RecordShare.

   В §7 и §15.6 собственная замена описана только для SSE защищённых объектов и для omni-событий. **Для webhook и logic function на обычных защищённых объектах (Person, Company, Opportunity) получатель после удаления Enterprise-кода не определён.** Достижимый сценарий: после удаления `RecordAccessPolicyService` webhook либо получает PRIVATE-записи, либо перестаёт работать, и контракта на этот случай нет.

   **Минимальная правка:**
   - Записать правило: функции, которые требуются по требованиям (фильтрация событий для webhook, logic function и SSE по защищённым объектам), получают собственную замену с principal интеграции и fail-closed. Функции, которые не требуются (validation rules, record sharing, RLS predicates, sharing запусков workflow и чатов агента), исключаются, а их точки входа явно отключаются. Это следует из R-12, а не из выбора за владельца.
   - Проверить, используются ли такие функции в экземпляре сейчас. Если используются, это вход для G18, а не умолчание.
   - T20 и T08: доставка webhook и logic function по PRIVATE-объекту без Enterprise-модулей.

2. **Порядка работ.** Manifest стоит в начале ROB-766, после ROB-764/765, которые уже опираются на эти пути (реестр потребителей §15.6). **Минимальная правка:** перенести в ROB-764 проверку в CI «новый код не добавляет зависимостей от файлов с пометкой Enterprise», зафиксировать известный список как baseline. Gate выпуска G18 остаётся как есть.

### L-7 (minor): штатная перепривязка участников не учтена в запрете
`MessageParticipantWorkspaceMemberListener`, при смене `userEmail`, запускает `matchParticipantsForWorkspaceMembers`. Тот не исключает APP-участников (сравните `:320`) и выполняет `updateMany` без подавления событий (`match-participant.service.ts:248-283`). Последствие зависит от того, как реализован запрет из §15.1:242.

- **Если запрет стоит на уровне репозитория для всех писателей,** конфиденциальность не страдает. Но транзакция job откатывается, и вместе с omni не перепривязываются email-участники этого сотрудника. Это регрессия совместимости, и T05 её не ловит.
- **Если запрет стоит только на generic API,** то обходится §15.6: UPDATED-события omni-участника (handle, displayName, messageId) уходят в webhook, workflow и timeline. Это утечка через события.

**Минимальная правка:**
- Внести этот job в перечень писателей §15.1:244 с решением «omni-участники исключаются так же, как `withoutAppChannelParticipants`».
- Согласовать §15.7:334: не полагаться на то, что перепривязка «может обнулить».
- T22/T05: смена email сотрудника даёт ноль изменений и ноль событий в omni, при этом email-участники перепривязываются.

### N-18 (minor, порождён правкой R3): метаданные omni-аккаунта видны всем
При `scope='WORKSPACE'` функция `findUsableByCaller` (`connected-account-metadata.service.ts:106-131`, resolver `:58`) и список каналов и папок по аккаунту (`message-channel-metadata.service.ts:95-110`) показывают handle, имя и каналы userbot-аккаунта любому участнику workspace. Это противоречит F-08 («видимость подключённых аккаунтов»). Изменения уже охраняются.

**Минимальная правка:** исключить аккаунты с omni-binding из этих списков, если у участника нет собственного права на binding, либо выбрать `scope='USER'` с custodian-владельцем. Тест T08: участник без права на binding аккаунт, канал и папки не видит.
