## Куда легли F1–F6

### F1 → H-3 (область чтения автономного принципала), major. Найдено в baseline, неполное исправление R1
- **Что уже покрыто в плане:**
  - §15.3:260 — generic read/search/groupBy/`execute_tool`/export подчиняются ResourceScope.
  - §9:140 — каждый turn и tool восстанавливает reference.
  - §9:146 — «credentials не выдаются по умолчанию».
  - Мутирующие tools проверяют epoch (§9:144). Поэтому `send_email` после takeover закрыт, и N-14 не переоткрывается.
- **Чего нет:** правила для делегированного токена, который действует вне процесса.
  - `code-interpreter-tool.ts:118-145,358-367` выпускает application access token на 5 минут. В нём только applicationId, userWorkspaceId и agentId, без conversation reference.
  - Песочница с этим токеном вызывает `/mcp execute_tool` — по сути новый входящий HTTP-запрос (`twenty-mcp-helper.const.ts:74-90`). У сервера нет связи этого запроса с captured ResourceScope, поэтому §15.3 к нему применить невозможно.
  - Закрытого allowlist инструментов в спецификации нет (grep по spec и ai-workflow-source: совпадений 0). `action-tool.provider.ts:66-254` раздаёт `http_request`, `send_email`, `code_interpreter` и другие по флагам роли.
  - Обязательного inventory инструментов, который мог бы это поймать, тоже нет.
- **Инвариант:** никакая учётная запись или токен, выпущенные из omni-запуска, не выходят за captured scope. Набор инструментов omni — закрытый allowlist, и он одинаков для показа модели и для исполнения.
- **Правка:**
  - В §9 или §15.3 явно задать allowlist.
  - Инструменты, которые выпускают токены, запретить, либо токен обязан нести reference и сервер его проверяет.
  - В T25 добавить негативные проверки трёх путей: прямой вызов, `execute_tool` и вызов из песочницы.

### F2 → M-7 (канонический durable trigger), major. Порождён правкой: ключ из R3 × lifecycle из R7
- **Что уже покрыто:** §15.10:363 формулирует сам инвариант: «поздняя публикация новой версии не переигрывает прошлое событие». T14 проверяет publish между созданием intent и стартом.
- **Чего нет:** единственный долговечный барьер — `UNIQUE(eventId, consumerId=workflowVersionId)` и `runId = f(eventId, versionId)` — зависит от версии.
  - §15.19:472 перед admission читает текущую подписку `UNIQUE(workspaceId, workflowId)`.
  - Код подтверждает, что при публикации версия меняется на месте: `core-workflow-lifecycle.workspace-service.ts:248-292`.
- **Сценарий:**
  1. Событие E получает квитанцию (E, v1), запуск R1 стартовал.
  2. Процесс падает до фиксации раздачи события.
  3. Администратор публикует v2.
  4. При восстановлении создаётся квитанция (E, v2) и запуск R2.
  5. Ключи `SEND_OMNI_MESSAGE` у R1 и R2 разные — клиент получает два сообщения.

  БД такой дубль не останавливает. Сам инвариант записан, но ограничение его не обеспечивает.
- **Правка:**
  - `consumerId = omni-workflow:{workflowId}`, версия хранится в квитанции как неизменяемое поле.
  - `runId = UUIDv5(workspace, eventId, workflowId)`.
  - Набор подписок для события фиксировать одним commit.
  - В T14 — publish до создания intent.

### F3 → N-3 (pausing AI занимает turn), minor. Неполное исправление R2
- **Что уже покрыто:** категория «upstream pausing tools» исключается и из показа модели, и из исполнения; T27 проверяет отсутствие starvation; при пробуждении reference и epoch проверяются заново (§9, §15.15), так что безопасность не страдает.
- **Чего нет:** нормативный перечень в §15.9:354 неполон:
  - нет `wait_for_duration` из `AGENT_WAIT_TOOL_NAMES`;
  - нет `ask_questions` из `PAUSING_TOOLS`;
  - wait tools передаются отдельным параметром `pausingTools: createAgentWaitTools()` (`agent-runner.service.ts:529`), а не через каталог.

  Обязательного inventory, который поймал бы пропуск, нет. Поэтому это дефект, а не просто «отсутствующий символ».
- **Правка:** исключения выводить из `PAUSING_TOOLS ∪ AGENT_WAIT_TOOL_NAMES`, в omni-запуске передавать `pausingTools: []`, добавить статический тест.

### F4 → M-13 (ограниченное число автоответов), minor. Порождён правкой: §15.14 из R5 × правило одного turn из R1
- **Что уже покрыто:** один активный turn (§15.3:266), slots эффектов (:264), лимит max effects в G07, явная route automation policy (§15.14).
- **Чего нет:** правило одного turn касается только OmniAutomationTurn. Admission различает effectKind, а G07 не говорит, что лимит действует на одно admission сразу для агента и для workflow.
- **Правка:** это не выбор за владельца, а оформление gate. В G07 записать: «бюджет ответа клиенту на одно admission общий для всех consumers». Пока явно не выбрано, кто отвечает, активация отправляющего workflow рядом с auto-агентом запрещена. Добавить вариант в T27.

## Замечание о лицензии
- **Текст LICENSE:** §13 AGPLv3 (строки 598-609). Изменённая версия, с которой пользователи работают по сети, должна заметно предлагать им Corresponding Source.
- **Что уже есть в плане:**
  - «LICENSE/notices сохраняются» (license-inventory, §15.13:402);
  - «права распространения проверяются до публикации runtime»;
  - G18 — preflight до production.
- **Пробел:** эти проверки привязаны к распространению или публикации. §13 срабатывает без распространения — при самом изменении кода и сетевом доступе пользователей.
- **Оценка:** это не новый корень. По модели отказов §1 технического сценария сбоя нет, поэтому это пункт release-чек-листа в G18: перед production обеспечить предложение исходников изменённой версии пользователям CRM. Правовую сертификацию живого экземпляра не даю.
