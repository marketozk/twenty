## 1. Вердикт

**Целиком к детальной реализации план не готов. Этапы 1 и 2a можно детализировать уже сейчас, после небольших дополнений к контрактам.**

Сильные стороны плана:
- транзакционная модель подтверждена кодом: единый `pg.PoolClient` в scope, запрет обычного `getRepository`, outbox вместо `afterCommit`;
- разделены `accepted`/`sent`/`unknown`;
- есть граница активации импорта (AutomationAdmission);
- лицензионная граница выдержана: нет обхода entitlement и копирования Enterprise RLS.

Найдено **6 серьёзных пробелов** (H-1…H-6). Каждый — реальный сценарий в рамках заданной модели отказов, и ни один не закрыт ни контрактом, ни тестом. Два из них подтверждены кодом: обходной путь чтения переписки (H-1) и штатные пути, удаляющие историю (H-2). Без исправления этап 3 может формально «пройти» матрицу и всё равно раскрыть переписку. Блокирующих противоречий для старта этапа 1 нет.

## 2. Пробелы и противоречия

### Серьёзные (High)

**H-1. Таймлайн переписки в карточке клиента обходит права. Этого пути нет в карте прав.** *Подтверждено кодом.*
- Где в коде: `TimelineMessagingService` читает `messageThread`/`messageParticipant` с `shouldBypassPermissionChecks: true` и системным контекстом (`timeline-messaging.service.ts:58-62, 129-133, 264-268, 320-324`) и отдаёт `lastMessageBody` (`:303`).
- Видимость считается по каналу целиком, а не по диалогу: `get-effective-message-channel-visibility.util.ts:10`, `format-threads.util.ts:35-41`. Владелец подключённого аккаунта видит **всё**.
- Резолвер проверяет только `AuthPrincipalGuard` и `CustomPermissionGuard` (`timeline-messaging.resolver.ts:97-110`). В `GetMessagesService` проверок прав нет.
- В плане этого пути нет: таблица в `access-source.md:13-28`, точки входа в `phase_3_access.md:9`.
- **Сценарий:** менеджер B видит Person X (например, тот относится к его сделке), но не допущен к диалогу X. B открывает карточку и получает темы и последнее сообщение через `getTimelineThreadsFromObjectRecord`/`searchTimelineThreads`. Требование «третий сотрудник не получает историю» (`requirements.md:130`) нарушено.
- **Нужно:**
  - внести timeline/search и `GetMessagesService` в карту прав;
  - для потоков omnichannel-каналов применять политику диалога вместо видимости канала (или исключить их из штатного таймлайна);
  - перечислить в реестре обходов прав (bypass inventory) все вызовы `shouldBypassPermissionChecks` для объектов `message*`.
- **Тест:** B без доступа к диалогу вызывает оба timeline-запроса и поиск — нет потоков, счётчиков и текста. Владелец `connectedAccount` без доступа к диалогу тоже ничего не получает.

**H-2. Штатные пути Twenty физически удаляют каноническую историю.** *Подтверждено кодом.*
- В коде:
  - `BlocklistItemDeleteMessagesJob` при добавлении handle в блок-лист удаляет сообщения во **всех** каналах workspace (`messaging-blocklist-item-delete-messages.job.ts:72-92`), затем запускает `cleanOrphanMessagesAndThreads`;
  - `MessagingMessageCleanerService` удаляет сообщения и потоки жёстко (`messaging-message-cleaner.service.ts:103, 120, 234`);
  - есть jobs очистки при удалении канала или подключённого аккаунта и команда `messaging-reset-channel`.
- В плане упомянуто только «не удалять весь channel» при откате (`phase_6_history.md:20`) и «disable сохраняет историю» (`04-testing.md:30`). Модель (`05-models.md:36`) не объявляет FK из core в workspace, поэтому `OmniMessageLink`, receipts и аудит останутся висячими.
- **Сценарий:** сотрудник вносит handle клиента в блок-лист, или владелец удаляет `connectedAccount` в настройках. Переписка безвозвратно удалена. Восстановить её из аудита нельзя: тексты туда намеренно не пишутся.
- **Нужно:**
  - описать контракт хранения omnichannel-истории: какие штатные чистильщики пропускают omni-каналы или требуют отдельного разрешённого действия;
  - отделить отключение привязки от удаления аккаунта;
  - аудировать purge.
- **Тест:** blocklist, удаление канала, удаление аккаунта, reset-channel на omni-канале — `Message`, ссылки и вложения сохраняются (либо операция отклоняется с записью в аудит).

**H-3. Не определено, от чьего имени и в какой области работает автономный ИИ.**
- Семантика «пересечение прав agent/application/caller и conversation policy» (`05-models.md:55`, `06-api.md:59-61`, `02-behavior.md:42-44`) в режиме `auto` не задана: человека-инициатора нет.
- По коду `runAsWorkspaceMemberId` требует application token (`ai-workflow-source.md:28`). Значит, автоответ будет идти от приложения с ролью уровня workspace.
- **Сценарий:** клиент X пишет «какой статус у заказа компании Y?». У агента-приложения есть право читать Opportunity, а `conversation policy` описана только для изменений. Generic `find_records` вернёт сделку Y, и модель процитирует её клиенту. Проверка «новое сообщение не подменяет scope» не спасает: scope был широким с самого начала.
- **Нужно:**
  - ввести отдельного субъекта автоответа (service principal, привязанный к диалогу);
  - **область чтения** = записи, связанные с подтверждёнными identity диалога, плюс база знаний; плюс явная таблица допустимых изменений;
  - описать, откуда берётся рамка для `assist` (менеджер) и для workflow.
- **Тест:** auto-run в диалоге X через generic read/search/groupBy/`execute_tool` не получает записи Y, хотя у роли приложения есть право на объект.
- Какие операции разрешать — продуктовое решение Q-05. Сам принцип «не шире связанных с клиентом записей» — архитектурный контракт.

**H-4. Повтор ИИ-прогона после сбоя может отправить клиенту второй ответ.**
- Ключ идемпотентности задан для браузера (`06-api.md:12`) и для workflow («command id от execution/action ID», `phase_5_ai_workflow.md:14`, `06-api.md:63`). Для ИИ-отправки ключ не задан.
- **Сценарий:** run сгенерировал ответ, вызвал send tool, создал команду — и процесс падает до сохранения результата turn. При восстановлении run (`agent-run-wait`: восстановление после падения держателя, `ai-workflow-source.md:192`) модель генерирует **новый** tool call с новым ID. Получается новая команда и второй ответ клиенту. Admission защищает от повторного запуска, но не от повторной отправки внутри одного допуска.
- **Нужно:** ключ ИИ-отправки детерминированно выводить из допуска на автоматическое действие (`admissionId` + `effectKind` + номер ответа), а не из ID tool call. Для одного допуска — не больше N внешних отправок, заданных политикой.
- **Тест:** kill воркера после создания команды до завершения turn → восстановление → одна команда.

**H-5. Восстановление из бэкапа: нет сверки с журналом коннектора и с допусками.**
- В плане есть только reconcile исходящих (`phase_7_acceptance.md:9, 18`).
- **Сценарий A, входящие:** до сбоя коннектор получил ACK на события 1000–1200 и считает их доставленными. После восстановления PostgreSQL Twenty этих receipts нет. Дефолтный retention коннектора — 30 дней (`research-connectors.md:93`), а на потерянное окно он отвечает HTTP 410 (`:39`). Входящие пропадают молча.
- **Сценарий B, повторные эффекты:** если события повторно пришли (replay), строки AutomationAdmission тоже откатились. ИИ повторно автоответит на сообщения, на которые уже ответил до сбоя: команды в Twenty утеряны, а у провайдера ответы есть.
- **Сценарий C, чужие квитанции:** коннектор присылает квитанции на `commandId`, о которых Twenty «не знает». Плюс расхождение `routeGeneration`.
- **Нужно:**
  - хранить по каждой привязке watermark последнего подтверждённого номера в журнале коннектора и уметь запросить replay с позиции;
  - коннектор хранит подтверждённые события не меньше интервала бэкапа;
  - после restore — режим «replay после восстановления», в котором автоэффекты для окна разрыва запрещены до сверки;
  - квитанции на неизвестные команды — в карантин с созданием исходящего Message без автора-менеджера;
  - сверка поколений маршрута.
- **Тест:** восстановить снимок до ACK → replay → нет дырок, ноль повторных автоответов, неизвестные квитанции разобраны.
- Связанный продуктовый пункт: политика бэкапов не выбрана (новый бэкап был сознательно пропущен, `current-steps.md:7`), а модель отказов требует «известный бэкап». Нужен gate: бэкап и проверенное восстановление обязательны **до** поступления реальной переписки.

**H-6. Исходящие сообщения не из CRM: телефон, SaleBot в переходе, MAX external API.**
- `02-behavior.md:34` сверяет только «собственное эхо» с командой. По коду коннекторов:
  - отправки из приложения владельца аккаунта отличаются от CRM-отправок (`research-connectors.md:84`);
  - в MAX `external_api.py:284 record_external_send` отправляет текст вне bridge (`:112`);
  - во время перехода SaleBot тоже шлёт через тот же аккаунт.
- **Сценарий:** в режиме `auto` сотрудник отвечает клиенту с телефона. Эхо без `commandId` либо теряется (нет правила), либо сопоставляется с ожидающей ИИ-командой по эвристике. В худшем случае ИИ тут же отправляет второй ответ. Takeover не срабатывает: человек действовал вне CRM.
- **Нужно:**
  - классифицировать исходящие без команды: `Message` с направлением outgoing, автор `external_sender(kind)`, никогда не запускает автоматику;
  - правило для `auto` (продуктовое: ставить ли ИИ на паузу, повышать ли `controlEpoch`);
  - сопоставлять эхо только по `commandId`/`random_id` из адаптера, без эвристики по тексту и времени.
- **Тест:** эхо без команды; эхо раньше `accept`; эхо при конкурирующей ИИ-команде.

### Мелкие (Low)

- **L-1. Замкнутая зависимость этапов 1 и 2a.** Этап 1 требует аудит в той же транзакции и проверяет «один audit success» (`phase_1_data.md:13, 15, 21`), а writer аудита отнесён к 2a (`README.md:9, 16`). Нужно указать, что ядро writer и сущность аудита входят в этап 1, а 2a расширяет охват.
- **L-2. Устаревшие места в документах.** `open-questions.md:24` («демо обновлено до 2.51») и `:29` («подтвердить transaction spike») противоречат `current-steps.md` и снятию spike.
- **L-3. Объём аудита.** Хук в `performInsert/performMutation` (`transactions-audit-source.md:73`) аудирует и системные писатели: синхронизацию почты, timeline-активности. Нужен реестр аудируемых объектов и оценка объёма (`08-audit.md:27`).
- **L-4. Повторная привязка аккаунта.** При disable → register нужно явно подтвердить, что `bindingId` стабилен (уникальность platform+account), иначе история разрежется по старой и новой привязке.
- **L-5. Отзыв штатных ролей Twenty.** `RoleService` и назначение роли участнику не берут собственный policy-fence (`integration-map.md:36`). Нужен тест гонки «отзыв штатной роли против ИИ-мутации».
- **L-6. Права на импорт.** Админа, запустившего импорт, нужно перепроверять на каждой пачке (`06-api.md:18`).
- **L-7. Изменяемость Message через generic API.** `Message`/`MessageThread`/`MessageParticipant` — штатные workspace-объекты. Критерий «нет открытого auto CRUD» (`phase_1_data.md:23`) должен явно включать запрет generic update/delete для строк omni-каналов.
