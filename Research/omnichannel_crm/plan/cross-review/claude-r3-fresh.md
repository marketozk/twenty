## Находки

**1. [High] Не описано, как workflow запускается от событий переписки (требование F-06).**
- Источники: requirements F-06:79-82. По §15.6:292-294 omni-записи пишутся без событий, а штатный слушатель database-workflow для omni не вызывается. По §15.3:257 нужна «единственная durable projection», но её форма нигде не определена. При этом §9:148, phase_5:7,17 и 06-api:49 всё ещё описывают передачу origin через `WorkspaceEventBatch`, что противоречит §15.6:292.
- Сценарий: администратор настраивает процесс «входящее сообщение → ответ из базы знаний». После ROB-764 штатный DATABASE_EVENT-триггер на `message` не сработает, а другой точки запуска нет. Есть и обратный риск: исполнитель включит события обратно и сломает подавление, которое проверяет T14.
- Исправление: выбрать одну форму триггера. Например, типизированный omni-триггер с видами message.received, conversation.created, assignment.changed и status.changed. Его сопоставляет consumer событий DomainEvent и передаёт в workflow безопасную проекцию данных.
  - Идентификатор запуска стабильный, считается из eventId и версии workflow. Существующий `CoreWorkflowRunnerService.run` уже принимает `workflowRunId` (`core-workflow-runner.service.ts:48-60,139`).
  - Нужны ConsumerReceipt на пару (eventId, версия workflow) и настройка триггера в редакторе workflow.
  - Устаревший текст про origin в phase_5 и 06-api удалить.
- Тест: расширить T14 — один запуск на событие при двух workers и потере Redis; импорт, эхо и заметки дают 0 запусков; штатный слушатель вызывается 0 раз.

**2. [Medium-High] Не определено, как ключи omni-сообщений ложатся на ключи дедупликации переиспользуемого кода.**
- Источники: `saveMessagesWithinTransaction` ищет существующее сообщение по `headerMessageId` во всём workspace, без фильтра по каналу (`messaging-message.service.ts:83-89`), и уникального индекса нет (`application-message-ingestion.service.ts:88`). Найденное сообщение переиспользуется, а его текст не обновляется (`:359-369`). В плане `headerMessageId`, `messageExternalId` и `messageThreadExternalId` не упоминаются.
- Сценарий А: у двух привязанных аккаунтов совпали «сырые» ID сообщений. Без пространства имён второе сообщение прицепится к первому Message. Дальше сработает `UNIQUE(workspaceId,messageId)` у MessageLink, и receipt будет бесконечно повторяться или уйдёт в карантин.
- Сценарий Б: в MAX сначала приходит пустая заглушка, потом заполненное сообщение (§15.2:237). Каноничное Message так и останется пустым.
- Исправление:
  - `headerMessageId` = версионированный хэш из (bindingId, providerChatId, canonical nativeMessageKey); `messageExternalId` = канонический ключ; `messageThreadExternalId` = providerChatId.
  - Переиспользуемый helper только создаёт сообщения. Заполнение заглушки, edit и delete идут через доменный путь ревизий (§15.5 OmniMessageRevision).
- Тест: в T01 — два аккаунта или чата с одинаковым сырым ID дают два Message. В T17 — заглушка, потом заполненное сообщение: одно Message с текстом и два receipts.

**3. [Medium] Переиспользование помощников противоречит подавлению событий.**
- Источники: `saveMessagesWithinTransaction`, `saveMessageParticipants` и `matchParticipants` берут репозитории без `repositoryOptions` (`messaging-message.service.ts:65-79`, `messaging-message-participant.service.ts:36`). Значит, события эмитятся (`workspace-repository.ts:1796`). phase_1:18 велит «вызвать существующий saveMessagesWithinTransaction», а §15.6:292 требует писать omni-данные без событий.
- Исправление: явно описать механизм. Вариант 1 — обёртка над transaction scope для omni, которая принудительно включает пропуск событий для message, messageThread, messageParticipant, association и targets. Вариант 2 — необязательный параметр у помощников; почтовый путь по умолчанию работает как раньше.
- Тест: отрицательный контроль в T14/T16 плюс проверка в T05, что почта по-прежнему эмитит события.

**4. [Medium-High] Не определено, что происходит, если менеджер отвечает в режиме auto без явного перехвата диалога.**
- Источники: требование F-04:69 — человек и ИИ не должны независимо отправлять конкурирующие ответы. Сейчас описаны только явный takeover (02-behavior:48, §9:144) и ответ с телефона в обход CRM (§15.2:243).
- Сценарий: ИИ формирует ответ, менеджер в это же время отправляет свой из композера. Уходят два конкурирующих ответа.
- Исправление: добавить продуктовый gate по аналогии с `externalHumanReplyPolicy`. Варианты: отправка менеджера атомарно выполняет takeover (epoch++, отмена ожидающих команд ИИ, тот же порядок блокировок); отправка запрещена до явного takeover; оба отвечают по явно принятому правилу. До выбора включение auto запрещено.
- Тест: расширить T24/T13 — активный ход ИИ плюс отправка менеджера дают поведение строго по выбранной политике.

**5. [Medium] Не описаны владелец omni ConnectedAccount и то, что происходит при удалении сотрудника.**
- Источники: поле `userWorkspaceId` обязательное (NOT NULL), `scope` по умолчанию USER (`connected-account.entity.ts:107,133`). При удалении участника все его аккаунты передаются хранителю: аккаунт архивируется, токены обнуляются, у канала ставится `isSyncEnabled=false` (`connected-account-ownership-transfer.service.ts:16-39`, `connected-account-metadata.service.ts:374-437`). Это не удаление, поэтому FK `RESTRICT` из §15.8 не сработает. T22 перечисляет только удаления.
- Сценарий: из workspace удаляют администратора, который подключал аккаунт. Общий канал молча архивируется. Если хранителя нет, остаётся висячий `userWorkspaceId`.
- Исправление: зафиксировать scope=WORKSPACE и владельца аккаунта. Источником истины считать статус AccountBinding. Lifecycle guard должен перехватывать и передачу владения с архивацией: либо перепривязка без архивации, либо отключение через доменную операцию с аудитом.
- Тест: в T22 — удаление сотрудника-владельца.

**6. [Low] Импорт истории: не описано, как сохраняются авторы (F-07:87).**
Исправление: хранить исходное имя или ID оператора как отметку о происхождении. Сопоставлять с сотрудником только по явному маппингу администратора; без маппинга автора не придумывать.
