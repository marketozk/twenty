## Остатки

### N-1 (major): текст переписки утекает через историю ИИ и запуски workflow
- **Сценарий.** Workflow по `message.received` вызывает scoped tool, тот читает тело сообщения и поля скрытой Person, результат сохраняется в `workflowRun.state`. Менеджер, которому виден этот workflow, но не разговор, читает текст через `workflowRuns` в API. Сейчас эти объекты защищает только upstream-флаг PRIVATE с доступом по workflow или ИИ-диалогу, а не по разговору (`standard-object-readability.spec.ts:66-77,92-117`).
- **Последствие.** Нарушен критерий приёмки «третий сотрудник не получает историю».
- **Как заметить.** Тело omni-сообщения появляется в ответе API `workflowRun`/`agentMessagePart` у сотрудника без доступа к разговору.
- **Обратимость.** Нет: раскрытые данные не вернуть.
- **Минимальная правка плана.** Внести эти объекты в §15.6 как производные от omni с правилом «доступ только если разрешены все раскрываемые родительские записи». Либо хранить для omni в `state` и в частях ИИ-сообщений только ссылки и redacted-данные. Расширить T21/T08, отрицательный контроль: снять redaction — тест падает.

### N-13 (major): Enterprise-код выполняется в общем пути запросов, а план это не учитывает
Разделяю факт по исходникам и юридический вывод.
- **Факт по исходникам.** `build-row-access-policy.util.ts` не помечен как Enterprise, но импортирует утилиты с заголовком `@license Enterprise` (`:4-6,14`) и вызывает `buildRecordShareGate` на каждом не-системном запросе (`:60`). Проверки ключа на этом пути я не нашёл. `resolveObjectSharing:58-59` выключает флагом только дополнительный режим sharing; ограничения PRIVATE и INHERITED действуют всегда. При этом `license-inventory.md:8,15` описывает ORM-путь как не-Enterprise и упоминает «entitlement gates».
- **Юридический вывод не установлен.** Условия Enterprise-лицензии я не читал. Из того, что код выполняется без проверки ключа, не следует ни нарушение, ни правомерность использования. Это needs_evidence.
- **Сценарий.** Формула §7 «existing grants AND own» и фактическая защита из N-1 молча опираются на этот код. Это противоречит действующему решению владельца: собственный ACL, без коммерческой runtime-зависимости.
- **Последствие.** Если позже этот код потребуется исключить, PRIVATE-объекты откроются, а план этого не предусматривает.
- **Как заметить.** Тесты собственного ACL проходят только при активном record-share gate.
- **Обратимость.** Технически обратимо.
- **Минимальная правка плана.**
  - Записать факт в license-inventory.
  - Требовать, чтобы собственный ACL и защита omni-производных данных не зависели от поведения record-share.
  - Проверить условия лицензии по тексту до реализации ROB-766.
  - В T20 добавить проверку PRIVATE- и INHERITED-объектов при выключенном или изолированном record-share.
  Подписку или одобрение нарушения у владельца не запрашиваю.

### N-14 (major): не определено, когда workflow может отправлять в диалог
- **Сценарий.** Менеджер сделал takeover. Новое сообщение клиента запускает workflow: ИИ-шаг готовит ответ, «Отправить в диалог» создаёт команду уже с новым `controlEpoch`. Takeover отменяет только pending-команды ИИ (§9:144, §15.11:362).
- **Последствие.** Нарушены F-04 и критерий «после передачи ИИ не отправляет».
- **Как заметить.** Исходящее сообщение с автором-workflow появляется после takeover.
- **Обратимость.** Нет: внешняя отправка уже состоялась.
- **Минимальная правка плана.**
  - Матрица в CommandService: тип отправителя (human / ai_turn / workflow / workflow с ИИ-контентом) × режим. Ответ, подготовленный ИИ внутри workflow, считается ответом ИИ.
  - Takeover отменяет не-человеческие pending-команды.
  - Служебные уведомления в режиме human — только по явному флагу.
  - Расширить T13/T24.

### N-15 (major, порождён правкой R2): что значит «проверить эпоху прав» и какие блокировки брать
- **Сценарий.** Общая эпоха прав workspace растёт при каждом изменении назначения или target (§7:116, §15.6:296). Экспорт проверяет её на каждой странице (§6:104), ходы ИИ и инструменты — перед записью. Если читать «проверку» как точное совпадение, обычная правка NoteTarget коллегой обрывает все экспорты и автоответы. Режимы блокировок не заданы, поэтому возможен deadlock при повышении FOR SHARE до FOR UPDATE: например, два одновременных merge.
- **Последствие.** Livelock экспорта и ИИ, все такие записи выстраиваются в очередь.
- **Как заметить.** Рост числа прерванных экспортов и ходов ИИ, ошибки 40P01 под обычной нагрузкой.
- **Обратимость.** Да.
- **Минимальная правка плана.**
  - Записать: несовпадение эпохи ведёт к повторной проверке прав, отказ — только если решение изменилось.
  - Читатели берут FOR SHARE; операции, которые увеличивают эпоху, берут FOR UPDATE сразу.
  - Расширить T10: несвязанные правки не обрывают экспорт, а revoke затронутых строк обрывает.

- **Как заметить.** У ImportBatch для native/archive нет реализуемого источника.

### M-7 (minor, порождён правкой R3): throttle при стабильном ID запуска
- **Сценарий.** При жёстком throttle `CoreWorkflowRunnerService.run` создаёт запуск со статусом FAILED под тем же детерминированным ID (`:112-148`). Повторная вставка с этим ID упадёт (`workflow-run.workspace-service.ts:99-101`). Фраза «resume того же run» этот случай не покрывает.
- **Последствие.** Автоматизация теряется, повтор с тем же ID невозможен.
- **Как заметить.** Запуск FAILED с ошибкой «Throttle limit reached».
- **Обратимость.** Да, через явный reprocess.
- **Минимальная правка плана.** Описать конечный исход «throttled» с видимой эскалацией и проверить его в T14.
