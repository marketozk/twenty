## Что подтвердилось по исходникам
- `upgrade-sequence-reader.service.ts:42-57` выстраивает команды группами fast → slow → workspace. Поэтому §15.5 верно говорит, что одного нового timestamp мало.
- `twenty-docker/twenty/entrypoint.sh:23-25` продолжает запуск после неудачного upgrade. Значит, штатный entrypoint действительно не может служить проверкой миграций.
- У `WorkspaceTransactionScope.getRepository` есть третий параметр `{shouldSkipEventEmission}`. Он подавляет и webhooks, и workflow, и timeline (`workspace-repository.ts:148-150`).
- `TimelineMessagingService` обходит проверку прав (`:61,132,267,323,436`) и отдаёт `lastMessageBody` (`:303`).
- `ConnectedAccount`: `applicationId` и `connectionProviderId` могут быть пустыми, при удалении срабатывает CASCADE; поля `scope` и `userWorkspaceId` NOT NULL. `transferOwnership` обнуляет токены и архивирует аккаунт (`connected-account-metadata.service.ts:415-431`).
- Публичный ingest для APP-каналов проверяет владельца через `findOwnedOrThrow(applicationId)`. Уникального индекса на `headerMessageId` нет, поиск по нему идёт по всему workspace.
- `CoreWorkflowRunnerService.run` принимает `workflowRunId`.
- Подтверждены: имена pausing tools, `Opportunity.stage: string`, отсутствие `searchVector` у Message, glob в core datasource и все перечисленные listeners и jobs.

## Замечания

### H1 (High): текст переписки утекает через историю ИИ и запуски workflow
- **Что упущено.** Каталог защищённых данных (§7, §15.6) не включает места, где ИИ и workflow сохраняют свои результаты:
  - `workflowRun.state` с результатами шагов;
  - `agentChatThread`, `agentMessage`, `agentMessagePart`, `agentTurn`, `agentChatThreadTarget`.
- **Что их сейчас закрывает.** Только upstream-флаги PRIVATE/INHERITED (`standard-object-readability.spec.ts:66-77,92-117`). По ним `workflowRun` видят те, кому выдан доступ к workflow, а ИИ-диалог — те, кому выдан доступ к этому диалогу. Доступ к самому разговору клиента здесь вообще не проверяется.
- **Сценарий.** Workflow по событию `message.received` вызывает scoped tool, и тот читает тело сообщения и поля скрытой Person. Результат шага ложится в `state`. Менеджер C видит этот workflow, но не имеет доступа к разговору, и читает текст через `workflowRuns` в generic API. Это прямо нарушает критерий приёмки «третий сотрудник… не получает историю… через UI/API/ИИ».
- **Минимальное исправление.**
  - Объявить эти объекты производными от omni с правилом «доступ только если разрешены все раскрываемые родительские записи».
  - Либо хранить для omni-запусков в `state` и в частях ИИ-сообщений только ссылки и redacted-данные, а сам контент держать в core `OmniAutomationTurn` под ACL разговора.
- **Тест.** Расширить T21/T08: сотрудник, которому доступны workflow и агент, но не разговор, не получает тело сообщения и CRM-поля через GraphQL, REST, поиск или экспорт `workflowRun`/`agentMessagePart`. Отрицательный контроль: снять redaction или правило — тест должен упасть.

### M1 (Medium): код с лицензией Enterprise выполняется без ключа, а инвентарь этого не отражает
- **Факт по коду.** `build-row-access-policy.util.ts` не помечен как Enterprise, но импортирует Enterprise-утилиты (`:4-6,14`) и вызывает `buildRecordShareGate` при каждом запросе (`:60`) без проверки ключа. Функция `resolveObjectSharing` (`:58-59`) отключает флагом только дополнительные возможности sharing. Ограничение PRIVATE/INHERITED работает всегда.
- **Противоречие.** `license-inventory.md:8,15` описывает ORM-путь как не-Enterprise и говорит об «entitlement gates». Формула решения §7 «existing grants AND own» молча включает этот код. Замечание H1 сейчас тоже опирается именно на него.
- **Что нужно от владельца (gate).** Допустимо ли работать с немодифицированным upstream, где этот код активен на Free. Если нет, его придётся заменить. Это решение не моё.
- **Исправление плана.**
  - Записать этот факт в инвентарь.
  - Явно запретить собственному ACL опираться на поведение record-share.
  - T20 должен проверять PRIVATE- и INHERITED-объекты без ключа.

### M2 (Medium): не определено, кто может отправлять из workflow в каждом режиме диалога
- **Что упущено.** Takeover отменяет только pending-команды ИИ (§9, §15.11). §15.10 разрешает отправку из workflow по `message.received`, но не задаёт правил по режимам human/assist/auto и по workflow с ИИ-шагом.
- **Сценарий.** Менеджер нажал takeover. Новое сообщение клиента запускает workflow: ИИ-шаг готовит ответ, действие «Отправить в диалог» создаёт Command уже с новым `controlEpoch` — и ответ уходит клиенту. Это нарушает F-04 и критерий «после передачи ИИ не отправляет».
- **Исправление.**
  - Таблица авторизации в CommandService: тип отправителя (human / ai_turn / workflow / workflow с ИИ-контентом) × режим. Ответ, подготовленный ИИ внутри workflow, считается ответом ИИ.
  - Takeover отменяет не-человеческие pending-команды.
  - Служебные уведомления в режиме human — только по явному флагу workflow. Если флаг нужен, это продуктовый gate.
- **Тест.** Расширить T13/T24: workflow с ИИ-шагом после takeover — 0 отправок. Уведомление о смене стадии сделки ведёт себя по выбранному флагу.

### M3 (Medium): неясно, что значит «проверить эпоху прав», и где здесь блокировки
- **Что в плане.** Одна общая эпоха прав на workspace (`WorkspacePolicyState`) увеличивается при revoke, при назначении (§7) и при каждом изменении parent/target (§15.6). Её проверяют экспорт на каждой странице (§6), курсор SSE (§8), ссылки ИИ (§9) и инструменты, которые меняют данные.
- **Почему это проблема.** Если «проверка» означает точное совпадение эпохи, обычная правка NoteTarget коллегой обрывает все экспорты и ход ИИ в workspace (livelock). Кроме того, эксклюзивная блокировка одной строки выстраивает все такие записи в очередь. Режимы блокировок не указаны, поэтому возможен deadlock при повышении FOR SHARE до FOR UPDATE: например, два одновременных merge.
- **Исправление.**
  - Записать, что несовпадение эпохи ведёт к повторной проверке прав по текущему состоянию. Отказ — только если решение изменилось.
  - Читатели берут FOR SHARE. Операции, которые увеличивают эпоху, берут FOR UPDATE сразу.
  - Изменения target/assignment при желании вести через отдельную ревизию области конкретного ресурса.
- **Тест (расширение T10).** Экспорт и ход ИИ завершаются при параллельных несвязанных правках. Revoke, который затрагивает выгружаемые строки, останавливает экспорт. Два merge без deadlock.

### M4 (Medium): у импорта нативной истории и архива коннектора нет транспортного пути
- **Противоречие.** §4: внешний JSON не может назначить происхождение «импорт», import job вызывает внутренний сервис. Но в 06-api в направлении Twenty→Connector есть только `enqueue`, `status`, `accountStatus` и `pause`, операции получения истории нет. Нативная история при этом живёт в юзерботах (`research-connectors.md:95-96`: окна до 24 часов, страницы до 100). Вдобавок 06-api всё ещё показывает поле `origin` в envelope и упоминает «import credential».
- **Исправление.**
  - Добавить pull-операцию `fetchHistoryPage(importBatchId, binding, chat, cursor, window, limit)` с отдельным credential только для импорта. Страница должна возвращать sourcePosition, native key, направление, вариант и pageHash.
  - Происхождение «импорт» назначает только job в Twenty.
  - Убрать `origin` из envelope v1.
- **Тест.** Контракт в T11 и overlap-сценарии в T16 для обоих каналов.

### Low
1. **L1.** Если workflow упирается в жёсткий throttle, `run` создаёт run в статусе FAILED с тем же детерминированным ID (`core-workflow-runner.service.ts:112-148`). Повторная вставка с этим ID упадёт (`workflow-run.workspace-service.ts:99-101`). Фраза «resume того же run» этот случай не покрывает. Нужен явный конечный исход «throttled» с эскалацией; проверить в T14.
2. **L2.** Решения владельца разбросаны по документу. `managerReplyPolicy`, политика очередей (QueueGrant), ответственный владелец аккаунта (custodian), размещение коннектора и владелец backup, хранение старого текста ревизий отсутствуют в §13 и в open-questions. Нужно свести их в одну таблицу.
3. **L3.** Поля envelope v1 описаны в разных местах: §4, §15.2 (направление, вариант, версия ключа), §15.7 (captureGeneration) и 06-api. Первым артефактом ROB-764 стоит сделать единую JSON Schema с контрактным тестом.
4. **L4.** `transitionOpportunity` принимает `expectedRevision`, но поля ревизии у Opportunity нет. Добавление стандартного поля не покрывает fork-runner, который работает только с core. Нужно выбрать CAS-токен: например, core-таблицу ревизий или `updatedAt`.
