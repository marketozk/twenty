# Требования: Twenty CRM вместо SaleBot

Версия: 0.5 от 26.10.2026. Последние уточнения: тендерный робот исключён; подписка Twenty не нужна, необходимые коммерческие возможности реализуем самостоятельно. Совместная работа менеджеров, максимальные полномочия ИИ внутри CRM и настройка доступа к сделкам/этапам сохраняются. Этот документ не разрешает переключение живых клиентов.

## 1. Цель

Принимать клиентские сообщения Telegram/MAX, вести диалоги и отвечать из Twenty. В одном рабочем месте доступны переписка, карточка клиента, сделки, задачи, рабочие процессы и ИИ. ИИ использует историю диалога, базу знаний и разрешённые CRM-данные.

Конечная система полностью заменяет SaleBot для общения. После перехода приём, хранение истории, ответы, ИИ и связанные с перепиской процессы не должны зависеть от API, интерфейса или хранилища SaleBot. SaleBot допустим как источник миграции и временный участник контролируемого перехода, а не как постоянная зависимость.

## 2. Решения, прямо подтверждённые пользователем

| ID | Решение |
|---|---|
| R-01 | Полная замена SaleBot для общения с клиентами, а не постоянный второй интерфейс поверх него. |
| R-02 | Максимально использовать существующий код и возможности Twenty. Не создавать вторую CRM рядом с Twenty без доказанной необходимости. |
| R-03 | Telegram и MAX должны входить в целевую функциональность. Имеющиеся юзерботы и коннекторы — исходная база для исследования. |
| R-04 | Рассмотреть отдельные юзерботы/коннекторы с API Twenty и встроенное подключение. Конкретное размещение и способ исполнения ещё не выбраны. |
| R-05 | Предусмотреть возможность переноса старой переписки. Фактический импорт, источник и объём согласуются отдельно. |
| R-06 | Переиспользовать интеграцию ИИ Twenty и сразу проектировать нужную функциональность, включая автоответы. Не ограничивать постановку только черновиками. |
| R-07 | Снято последним уточнением пользователя: интеграция с тендерным роботом не входит в проект. ID сохранён для ссылок из прежнего исследования. |
| R-08 | Создать отдельную папку проекта на Рабочем столе; хранить здесь документы и новый код доработки. |
| R-09 | Несколько менеджеров могут общаться с клиентом в одном диалоге CRM. У менеджеров отдельные входы и разграничение видимости/действий. |
| R-10 | ИИ проектируется с максимальными функциональными полномочиями внутри CRM: ответы клиентам, выполнение доступных операций CRM и запуск рабочих процессов. Конкретные операции, права и условия выполнения описываются в матрице инструментов. |
| R-11 | Видимость сделок и этапов настраивается для сотрудников. При проектировании отдельно определить чтение, редактирование и разрешённые переходы между этапами. |
| R-12 | Работа без подписки Twenty. Нужные функции из коммерческого набора, прежде всего ограничения доступа и аудит, реализуем самостоятельно на разрешённой основе. Не подключаем коммерческую runtime-зависимость и не считаем копирование её реализации собственной разработкой. Это не добавляет весь Enterprise-каталог в обязательный объём. |

## 3. Функциональный состав

Ниже — рабочая детализация обсуждённой задачи. Она не закрывает вопросы раздела 7 и не подтверждает заранее доступность функций через API конкретного канала.

### F-01. Подключения и маршруты

- Личные диалоги Telegram/MAX через подключённые аккаунты.
- Учёт платформы, конкретного подключённого аккаунта и конкретного чата. Ответ возвращается по выбранному маршруту, а не в случайный канал того же клиента.
- Видимость состояния подключения, ошибок и необходимости повторной авторизации.
- Модель данных должна различать аккаунты и их диалоги. Число аккаунтов и организационных рабочих областей уточняется.
- Основной сценарий — существующие юзерботы. Отдельные бот-аккаунты через Bot API не входят в подтверждённый обязательный объём; дополнительное подключение этого типа не является условием использования CRM.
- Совместная работа нескольких менеджеров в одном клиентском диалоге обязательна. Это не требует превращать личный чат клиента в группу мессенджера. Поддержка собственно внешних групп Telegram/MAX с несколькими участниками отдельно не подтверждена.
- Подключение и управление должны быть понятны администратору CRM. Нужно ли выполнять вход/QR/переподключение прямо в Twenty — открытый продуктовый вопрос.

### F-02. Рабочее место оператора

- Раздел «Чаты»: список диалогов, поиск, непрочитанные, фильтры по платформе, аккаунту, ответственному и состоянию обращения.
- Просмотр переписки, отправка текста и поддерживаемых вложений. Матрица изображений, документов, голосовых, видео, ответов на сообщения и других типов уточняется по каналам.
- Понятные состояния исходящего сообщения: ожидает отправки, подтверждённая отправка, ошибка, неизвестный результат. «Доставлено» и «Прочитано» показываются только если канал действительно это подтверждает.
- Назначение ответственного, передача диалога человеку, закрытие/возобновление обращения.
- Несколько допущенных менеджеров могут читать один диалог и отвечать в нём со своих CRM-учётных записей. Внутри CRM у каждого сообщения виден конкретный автор; наружу сообщение уходит через выбранный подключённый аккаунт. Представление имени менеджера клиенту (например, подпись) настраивается отдельно и не имитирует отдельный Telegram/MAX-аккаунт.
- Различать ответственного за диалог и сотрудников, которым разрешено участвовать. Продумать видимость текущей работы коллеги и предотвращение случайных конкурирующих ответов без запрета совместного обслуживания.
- Внутренние заметки отделены от сообщений клиенту.
- Идентичность автора (оператор/ИИ) видна в истории действий.
- Интерфейс проектируется в согласованном направлении нового ЛК; прежний макет «Возможности» — визуальный ориентир, не готовый экран чатов.

### F-03. Связь с CRM

- Диалог связан с контактом; при необходимости с компанией, сделкой и задачами.
- Из диалога можно перейти в карточку и создать связанные CRM-сущности.
- Каналы одного клиента можно объединить на уровне карточки после подтверждения соответствия. Переписки и адреса доставки сохраняются раздельно.
- Стандартные сущности, связи, поиск, роли, автоматизации и журналирование Twenty переиспользуются там, где их контракт подходит.

### F-04. ИИ

- Черновик ответа, помощь в формулировке, резюме диалога и автоматический ответ по настроенным правилам.
- Использование истории диалога, базы знаний и разрешённых CRM-данных.
- Максимально полный набор прикладных действий CRM: ответы клиентам, создание/изменение CRM-записей, запуск рабочих процессов через доступные инструменты. Перечень и реальные возможности инструментов подтвердить по коду/API.
- Полномочия инструментов проверяются сервером, а не только инструкцией модели. Для каждого действия определить инициатора, область доступа, условия выполнения, результат и журналирование; обязательное ручное подтверждение каждого сообщения заранее не навязывается.
- Сначала исследовать существующие провайдеры, агентов, skills, инструменты и рабочие процессы Twenty. Новый независимый ИИ-сервис не считается решением по умолчанию.
- Предусмотреть настройку автоответов и передачу диалога оператору. Человек и ИИ не должны независимо отправлять конкурирующие ответы на одно обращение.
- При недоступности данных ИИ не выдумывает статус: сообщает об ограничении либо передаёт вопрос человеку по заданному правилу.
- Конкретная модель, провайдер, стоимость и лимиты определяются после проверки текущей интеграции. Наличие кода интеграции не означает, что провайдер уже настроен в нашем экземпляре.

### F-05. Исключено из объёма

Прежний раздел о данных и действиях тендерного робота снят пользователем. Он не является зависимостью, этапом реализации или критерием приёмки CRM. Юзерботы Telegram/MAX остаются транспортом сообщений по F-01 и не относятся к этой исключённой интеграции.

### F-06. Рабочие процессы

- Входящее сообщение, новый диалог, изменение ответственного/состояния и другие согласованные события могут запускать процессы Twenty.
- Действия процессов могут создавать/обновлять CRM-записи, вызывать инструменты ИИ и инициировать отправку по конкретному маршруту.
- Пример: обращение → определить клиента → найти ответ в базе знаний → подготовить/отправить ответ по правилам.
- Пример: изменение этапа сделки → назначить задачу менеджеру → отправить согласованное уведомление клиенту.
- Разделить клиентские сообщения, внутренние заметки и служебные события, чтобы не запускать бесконечные циклы автоматизаций.

### F-07. Перенос истории

- Возможность импорта старых сообщений с сохранением доступных дат, направлений, авторов, канала/аккаунта, связей и вложений.
- Рассмотреть источники SaleBot, существующий коннектор/архив и сами платформы; фактическую полноту каждого подтвердить исследованием.
- Повторный импорт не создаёт дубликаты; есть прогресс, контрольная сверка и отчёт о пропусках.
- Недоступные исходные файлы/сообщения отмечаются явно; не обещать восстановить то, чего нет у источника.
- Импортированные сообщения не вызывают новые автоответы и уведомления как свежие входящие.
- Граница старой истории и новых событий, продолжение прерванного импорта и переключение системы должны быть спроектированы.

### F-08. Менеджеры и видимость

- Отдельная учётная запись и сессия у каждого сотрудника; общий пароль оператора не используется как модель доступа.
- Разграничение видимости диалогов, контактов, компаний, сделок, этапов и подключённых аккаунтов; аналогичные проверки распространяются на API, поиск, вложения, экспорт и ИИ-инструменты.
- Настраивать набор доступных сделок по правилам назначения, команды и явного доступа, а также доступ к воронкам/этапам. Конкретная комбинация правил определяется в матрице ролей.
- Различать право видеть этап и его сделки, право редактировать сделку, право переводить её между этапами и право менять настройки самой воронки. Скрытие колонки интерфейса не заменяет серверный контроль доступа.
- Недоступные сделки не раскрываются через прямые ссылки, поиск, отчёты, счётчики и суммы канбана, экспорт, API или ответы ИИ. При переходе сделки в недоступный этап видимость пересчитывается по правилам доступа.
- Предварительная ролевая схема для исследования: менеджер — назначенные/разрешённые клиенты, руководитель — доступ своей команды, администратор — управление доступом в своей рабочей области. Конкретные роли и правила распределения ещё уточняются.
- Несколько сотрудников получают доступ к одному диалогу по правилам совместной работы; передача ответственности не уничтожает историю авторства.
- Переиспользовать подходящие механизмы доступа Twenty; достаточность, ограничения и доступность этих механизмов в выбранной редакции проверить до решения о доработке.

## 4. Надёжность и доступ

- История и принятые задания сохраняются после перезапуска; подтверждение приёма выдаётся после надёжного сохранения.
- Повторные события и команды не порождают неконтролируемые дубликаты.
- Потерянный ответ внешнего сервиса не равнозначен отсутствию отправки. Неопределённый результат учитывается отдельно; повторы зависят от гарантий конкретного API.
- Проверяются права рабочего пространства, оператора, клиента и подключённого аккаунта.
- Токены, сессии юзерботов, ключи ИИ и реальные переписки не попадают в Git, клиентский JavaScript или публичные отчёты.
- Для передачи диалога человеку, автоответов и исходящих сообщений нужны согласованные правила конкурентного доступа и журнал действий.
- Количественные цели скорости, нагрузки, хранения и восстановления задаются после определения масштаба. Произвольные SLA сейчас не назначены.

## 5. Критерии результата

| Проверка | Наблюдаемый результат |
|---|---|
| Telegram и MAX | Сообщение появляется в нужном диалоге; ответ оператора возвращается через правильный аккаунт. |
| Связь клиента | Переписка и CRM-данные связаны корректно; чужие данные недоступны. |
| Совместная работа | Два менеджера с отдельными входами участвуют в разрешённом общем диалоге; авторы различимы; третий сотрудник без доступа не получает историю, вложения и связанные данные через UI/API/ИИ. |
| Сделки и этапы | Сотрудник видит только разрешённые сделки/этапы во всех представлениях; изменение фильтра или прямой запрос не обходит ограничения; запрещённый переход отклоняется сервером. |
| ИИ | Работают черновик, разрешённый автоответ и согласованные операции CRM; используются переписка, база знаний и разрешённые CRM-данные, проверяются полномочия и сохраняется результат действия. |
| Передача человеку | После передачи ИИ не отправляет устаревший конкурирующий ответ. |
| Импорт | Старые данные доступны в переписке; повторный запуск не дублирует их и не запускает автоответы. |
| Сбой/повтор | Перезапуск, повтор события и неизвестный результат отправки обработаны в рамках документированной модели отказов. |
| Независимость | После завершения перехода переписка работает при недоступном SaleBot, без его credentials и хранилища в рабочем пути. |
| Переиспользование | Для новых механизмов показано, почему существующего механизма Twenty недостаточно; сохранена совместимость с обновлениями в выбранных границах. |

## 6. Границы текущего шага

Требования зафиксированы; по последующим запросам выполнены исследование, обновление официального демо и выбор базы исходников. Сейчас записана архитектура v1. Этот этап не запускает разработку нового runtime, живой импорт, отправку сообщений, автоответы клиентам, отключение SaleBot или изменение авторизации аккаунтов.

Разбиение реализации на проверяемые этапы не отменяет полного состава требований: нужны Telegram и MAX, ответы менеджеров, автоответы ИИ и операции CRM. Интеграция с тендерным роботом в состав требований не входит.

## 7. Открытые решения

См. [open-questions.md](open-questions.md) и [архитектуру v1](design/01-architecture.md). Выбраны модуль внутри форка, отдельный транспорт, Message/MessageThread, нативный экран с authenticated subscriptions и собственные права без подписки. Открыты конкретное размещение сервисов, UI авторизации аккаунтов, провайдер ИИ, внешние группы/дополнительные бот-аккаунты, объём миграции, матрица ролей и условия инструментов. Совместная работа менеджеров и максимальная функциональность ИИ уже входят в требования.
