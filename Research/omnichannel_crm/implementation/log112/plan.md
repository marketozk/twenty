# LOG112 — public/AI role CREATE audit

Research: RoleResolver.createOneRole и CreateRoleTool вызывают RoleService.createRole.
Тот же метод используется member/guest/bootstrap/seeder. Registered metadata side-effect
handlers не содержат role/create; обычный create создаёт одну role строку. Existing
CreateRoleActionHandler использует enriched action.id, иначе генерирует UUID; его
workspace schema handler пустой. Normalizer уже задаёт defaults/trim и relation arrays.

Решение: отдельный обязательный audited create entry для resolver/tool с переиспользованием
существующего create body. Internal bootstrap/member/guest/seeder остаётся явным legacy
путём без выдуманного user actor. Расширяем bounded role audit scope и runner CREATE:
фиксируем normalized role ID/universal ID/application/workspace, проверяем final single
create action + enriched ID, actual insert snapshot и post-flush state. Один strict
owner, admin descriptor и cache invalidation после unknown как в LOG111.

Не используем after-commit events как audit и не переносим create SQL в resolver.
Не включаем роль DELETE/assignments и системные metadata migrations без их проверки.
Tests: actual create service/tool/handler/runner, defaults/trim/null, autogenerated и
explicit ID, duplicate ID, wrong final ID/scope/application, extra/deferred action,
audit/SQL failure, corrupting trigger, lost ACK, bootstrap path без ложной attribution.
