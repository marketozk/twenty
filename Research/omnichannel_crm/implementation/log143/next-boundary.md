# LOG144 — next calendar matching boundary (read-only proposal)

Status: source research only. No implementation, runtime test, deployment or acceptance claim. Checkout was read while LOG143 was being integrated. All paths below are relative to `packages/twenty-server/` in `C:/Users/regis/OneDrive/Рабочий стол/Twenty CRM`.

## Recommended smallest coherent slice

Close the **calendar import postcommit participant rematch plus calendar target reconciliation** as one strict/exclusive audited transaction. Keep contact/company creation and durable queue delivery explicitly outside this slice. Do not expand the generic matcher to all messaging callers or advertise the entire calendar/contact lifecycle as covered.

Why combine these two writes: the current calendar call updates Participant.personId/workspaceMemberId, then derives CalendarEventTarget from the resulting Person links. Auditing only the target stage leaves the directly preceding system link mutation unaudited; putting each stage in a separately finalized owner permits partial matching with stale targets. Reuse the established target algorithm and audit primitives, not the message-thread-specific exported owner. A standalone calendar target owner is a smaller preparatory step, but does not close this import boundary by itself.

## Existing reusable code and limitations

- `src/engine/core-modules/crm-audit/native-message-cleanup-with-audit.ts::reconcileTargetsStage` (~938) and exported `reconcileNativeMessageThreadTargetsWithAudit` (~1832) already demonstrate closed actual-only target auditing: original issued system scope, bounded input, exact standard metadata, source/FK locks, snapshot comparison, actual RETURNING sets, incoming UPDATE/DELETE effect refusal, one flush and deferred validation. Its graph and ownership rules are specifically Thread -> Message -> Participant -> Person/Company/Opportunity -> messageThreadTarget. It cannot be invoked for CalendarEventTarget or after arbitrary mutations in the same scope as though it were a general stage.
- Reuse `computeTargetReconciliationOperations` from the existing pure utility. It already preserves manual assignments, automatic flags, obsolete automatic target deletion and tombstones; no external type/EE imports.
- Reuse actual metadata/snapshot/executor/FK helpers (`getIssuedNativeCleanupMetadata`, `createCrmAuditWorkspaceExecutor`, `readNativeCrmAuditRows`, `captureNativeCrmAuditSnapshot`, `assertNoReferentialUpdateEffects`) and LOG143 final validation approach. Keep new stage composition private; no caller-supplied audit context, callbacks or deletion/update masks.
- Generic `nativeAudit` on the transaction is NOT a substitute: `native-crm-audit-record.ts:52-99` admits Company/Person/Opportunity and eligible custom objects; CalendarEventParticipant/CalendarEventTarget are excluded. The current matcher does not supply nativeAudit anyway. Ordinary system workspace context alone does not create an audit context.
- `WorkspaceOrmManager.executeInWorkspaceContext` loads/authenticates context; only runInWorkspaceTransaction opens a transaction. Existing rematch helpers do call runInWorkspaceTransaction but without the strict/exclusive owner or audit operation required here.

## Preserve exact business semantics

- Participants for this import are **actual saved participant IDs**, and targets cover **all returned calendar event IDs**. Empty saved participant list still reconciles targets; empty/no-change link mutations must not fabricate audit entries.
- Participant source payload is only a candidate hint. Re-read and lock current native rows and their parent Event before mutation; never use stale handle, personId, workspaceMemberId or eventId as final authority.
- Person matching queries `addPersonEmailFiltersToQueryBuilder`, which explicitly uses withDeleted. It considers primary emails case-insensitively; additional-email candidate selection is JSONB containment of normalized input. The selection helper prefers a matching primary email over any additional email; candidate order is createdAt ASC. Do not silently change this to live-only matching or add a new tie-break policy in an audit change.
- WorkspaceMember matching uses live repository.find and exact userEmail equality, unlike case-insensitive Person matching. Preserve this difference.
- Calendar targets use live Participants and live People, so a Participant link to a soft-deleted Person does not produce an automatic target. The existing target service emits companyId from the live Person and live Opportunities without a separate explicit Company liveness query; preserve the existing policy rather than importing unrelated changes from the message owner.
- Only personId/workspaceMemberId are writable in the matching stage. Do not update handle, event association, responseStatus or organizer fields from stale DTOs. Preserve ordered matching modes; workspaceMemberOnly currently skips target reconciliation, targetsOnly skips email matching entirely. These broader modes need not be exposed by the initial import-only owner.
- Standard metadata has Participant.event CASCADE and Participant.person/workspaceMember SET NULL; Target.event CASCADE, typed target relations and per-parent/target unique indexes. Verify the deployed actual FK graph before using row locks as insertion fences. Existing helpers must refuse populated unsupported incoming effects on changed participant/target columns.
- Lock candidate Event roots, relevant Participants, matching Person/WorkspaceMember sources, linked Company/Opportunity sources and existing targets in a deterministic order. Protect absence predicates and source selection through fixed selectors and final rereads; simple locks on the initially found Person rows do not freeze a previously absent email candidate. Establish a serializable/cooperative scope guarantee explicitly, not a claim that row locks fence all raw SQL email changes.
- Exact final graph must allow only actual returned link updates/target effects, and verify retained sources before target-stage snapshots adopt them. Revalidate after audit flush and deferred constraint drain. Earlier Participant changes must not legitimize unrelated trigger writes to other sources/targets.

## No new enterprise dependency edge recommendation

Retain the coordinator in an existing service that already owns the relevant dependencies: CalendarEventParticipantService already imports MatchParticipantService; MatchParticipantService already imports the old target reconciler and entity/ORM types. Add a calendar-specific closed entry there, or a new structural leaf owner that imports only verified leaf audit/pure policy utilities. Do not create a new module importing MatchParticipantService, entity classes, WorkspaceOrmManager, shared type barrels, or existing query-builder helpers solely for convenience.

In particular, `findPersonByPrimaryOrAdditionalEmail.ts` imports PersonWorkspaceEntity (type-only still forms an edge in the guard), and `addPersonEmailFiltersToQueryBuilder.ts` imports the full query-builder graph. Reuse them inside their existing service dependency boundary, or make a deliberately structural pure projection with equivalent tests; do not assume a new owner importing those utilities is EE-safe. `computeTargetReconciliationOperations` has no imports and is the safe direct reuse point.

`scripts/omnichannel/check_enterprise_dependencies.py:202-250` records new runtime reachability and new edges into the enterprise-reaching closure. Keep pinned baseline unchanged. This is a proposed path; only the actual implementation guard can confirm its resulting dependency graph.

## Attribution and postcommit behavior

- Capture workspace, IDs, mode and operation before the first await. Named system actor must be created in trusted service/job code (existing systemMembershipCleanupIdentity + membershipCleanupOperation), not taken from contacts or payload account owner. FieldActorSource.CALENDAR and createdBy.workspaceMember are business provenance, not proof of the current audit actor.
- Use a fresh matching operation separate from the committed save operation. It can retain captured save correlation/causation if deliberately passed through the existing coordinator; an audit operation is not a delivery receipt or retry key.
- Keep the existing order **enqueue contact job -> matching** unless explicitly changing the product contract. Queue enqueue is not part of the database transaction. A later matching failure cannot undo a successful enqueue or the LOG143 save. Conversely enqueue failure currently prevents matching. Tests must document this partial-outcome boundary.
- LOG143 CoreAuditPostCommitError prevents retrying the whole already committed save to repair a failed followup. Do not catch it and replay provider save or resend the queue payload. A new matching owner must preserve unknown-commit/rollback-failure instances; actual queue drivers discard recognized unsafe outcomes only if the error reaches them.
- `MessageQueueService.add` delegates to the driver; this call supplies no job ID or retry options. BullMQ buildJobsOptions uses attempts = 1 + retryLimit (default one attempt); even an optional caller ID is suffixed with a random UUID. Thus this path has neither demonstrated durable outbox nor deduplicated enqueue/recovery. Do not claim guaranteed contact-job delivery, exactly-once processing or automatic recovery from audit IDs.
- `createCompaniesAndPeopleAndUpdateParticipants` currently swallows every non-duplicate batch error after reporting. Before that job can use audited owners, it must rethrow isTransactionUnsafeToRetry before logging/classifying, preserving the original instance and stopping later batches. Ordinary duplicate/ordinary-error policy should not be broadly changed in this calendar matching slice.

## Explicit remaining contact-creation gap (separate implementation boundary)

- `CreateCompanyService.createOrRestoreCompanies` performs Company.save and restore updateMany; `CreatePersonService` performs Person.insert, restore deletedAt/companyId and name-enrichment updateMany. These are ordinary system repository calls without nativeAudit transaction options. Generic native Company/Person audit machinery exists, but is not active here.
- Company enrichment performs an HTTP domain lookup in prepareCompanyData before writes. Do not wrap that network request in the future database lock/transaction. Capture external prepared values before the closed owner; validate current matching/restoration authority again under locks.
- Account ownership/provider/aliases and channel auto-creation permission in the current queue path originate from captured objects, not fresh locked current rows. Job membership lookup uses an ID without explicit workspace binding in that query. A future contact owner must establish fresh scope/authority, rather than treating the old payload as current authorization.
- Person/Company batch operations are not one atomic transaction; partial changes can survive later failure. Their created/updated events feed the separate rematch jobs. Closing those writes must preserve event emission and deliberately address postcommit failures and duplicate entry handling. Not part of this proposal's claim.
- CalendarEventParticipantMatchParticipantJob, direct calendar matcher callers and calendar branch of ReconcilePersonCompanyTargetsJob still require explicit migration if only the import entry is changed. Existing messaging rematch behavior remains outside this narrowly selected slice.

## Minimum evidence for the proposed slice

1. Real matching + target PG success: actual participant link audit and Person/Company/Opportunity targets in one operation, unchanged responseStatus/organizer fields, no-op repeat emits nothing.
2. Primary-vs-additional matching, case behavior, withDeleted Person vs live target derivation, empty saved participant list, linked-event-only targets, stale/moved/deleted participant hint.
3. Manual/tombstone policy; actual skipped Participant UPDATE and Target INSERT/UPDATE/DELETE; matching must derive targets from actual applied links, not proposed updates.
4. Participant update succeeds but target mutation/audit insert fails -> whole matching/target transaction rolls back; pre-existing save remains committed. Source mutations by ordinary/deferred triggers fail final exact proof.
5. Missing expected FK, populated unknown incoming CASCADE/SET NULL/ON UPDATE effects; source reparent before/after locks; concurrent source creation candidate edge; exact generated/timestamp postimages.
6. Unknown COMMIT preserves the original error and actual committed audit/data; no save replay, no duplicate enqueue by catch logic. Queue already-enqueued + later matcher failure and queue-failure-before-matching tested at real coordinator boundary.
7. Actual service/job attribution capture, strict/exclusive original issued scope, workspace mismatch and missing operation rejected before writes. No expansion of nativeAudit whitelist.
