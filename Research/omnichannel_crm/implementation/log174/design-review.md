# LOG-174 - Независимое ревью дизайна (`design-review.md`)

## 1. Вердикт

- Первичный проход: `Changes Requested` (`5 major`, `5 minor`, `0 blocker`).
- Повторная сверка после внесения правок в `design.md` и `test-research.md`: `PASS` (`0` открытых замечаний).

## 2. Находки независимого ревью и их разрешение

| # | Серьёзность | Находка | Решение в дизайне и коде |
|---|---|---|---|
| D1 | `major` | При захвате идентичности из GraphQL-контекста для `oauthClient` / `application` в режиме `withUser` (`req.application` + `req.user`) стандартный `roleAuditIdentityFromRequest` выбирает ветку `user` и теряет `req.application`, искажая `actor`/`initiator`. | В `workspace-domain-audit.ts` реализован явный экстрактор идентичности: при наличии `application` и `user` выставляется `actor: { kind: 'application', id: application.id }` (или `agent`) и `initiator: { kind: 'coreUser', id: user.id }`; при `withoutUser` выставляется `actor: { kind: 'application', id: application.id }`; неоднозначные комбинации (`apiKey` + `user`/`application`, `impersonationContext` + `apiKey`/`application`, `agentId` без `application`) отвергаются. |
| D2 | `major` | В `PublicDomainService.createPublicDomain` предварительная проверка дубликата была ограничена `workspace.id`, а безусловный вызов `deleteHostnameSilently` в `catch` вокруг `runAuditedPublicDomainCreate` при ошибке `PUBLIC_DOMAIN_ALREADY_REGISTERED` / `DOMAIN_ALREADY_REGISTERED_AS_CUSTOM_DOMAIN` удалил бы чужой боевой хост из Cloudflare. | Предварительная проверка заменена на глобальную `publicDomainRepositoryUnscoped.findOne({ where: { domain: formattedDomain } })`, а в блоке `catch` вокруг `runAuditedPublicDomainCreate` компенсирующий вызов `deleteHostnameSilently` не выполняется при `NativeTransactionOutcomeUnknownError`, `CoreAuditPostCommitError` и `PublicDomainException` с кодами `PUBLIC_DOMAIN_ALREADY_REGISTERED` / `DOMAIN_ALREADY_REGISTERED_AS_CUSTOM_DOMAIN`. |
| D3 | `major` | Между `core.application` и `core."publicDomain"` действуют встречные FK (`applicationId -> application(id) ON DELETE CASCADE` и `primaryPublicDomainId -> publicDomain(id) ON DELETE SET NULL`); удаление `core."publicDomain"` без предварительной блокировки `core.application` инвертирует порядок блокировок `core.application -> core."publicDomain"`. | Во всех операциях `workspace-domain-audit.ts` и `runAuditedApplicationDelete` зафиксирован строгий порядок блокировок (`core.workspace` -> таблицы субъекта -> `core.application` -> `core."applicationAuthorization"` -> `core."publicDomain"` -> `core."approvedAccessDomain"`), а в `runAuditedPublicDomainDelete` и `runAuditedPublicDomainValidationUpdate` целевое `core.application` блокируется `FOR NO KEY UPDATE` до модификации/удаления `core."publicDomain"`. |
| D4 | `major` | В `CheckPublicDomainsValidRecordsCronJob.handle` и `DnsCloudflareService.checkHostname` требуется явная передача системной идентичности (`CheckPublicDomainsValidRecordsCronJob` и `DnsCloudflareService.checkHostname`), а в `PublicDomainService.checkPublicDomainValidRecords` сравнение `isValidated` должно выполняться по заблокированной `FOR UPDATE` строке БД, а не по устаревшему значению в памяти. | `CheckPublicDomainsValidRecordsCronJob.handle` и `DnsCloudflareService.checkHostname` явно передают свой `auditIdentity`; `PublicDomainService.checkPublicDomainValidRecords` не допускает неявного fallback'а на `system` и при наличии `coreDataSource` всегда вызывает `runAuditedPublicDomainValidationUpdate`, где `Boolean(beforeRow.isValidated) === isValidated` проверяется под `FOR UPDATE`. |
| D5 | `major` | Использование одного и того же `AsyncLocalStorage` для `withWorkspaceDomainAudit` в резолвере и для `registerMetadataAuditScopeCheck` заблокирует вызов сервиса из резолвера как вложенную транзакцию либо допустит реентерабельную мутацию внутри `onAfterAuditFlush`. | Ambient-скоуп `withWorkspaceDomainAudit` и одноразовый `WorkspaceDomainAuditRequest` отделены от эксклюзивного транзакционного скоупа `withExclusiveAuditScope` (регистрируемого в `registerMetadataAuditScopeCheck(getWorkspaceDomainAudit)` и активного только вокруг `runInCoreAuditTransaction`). |
| D6 | `minor` | `ApprovedAccessDomainResolver.createApprovedAccessDomain` требует `@AuthUser() currentUser` для загрузки `workspaceMember` отправителя письма, поэтому аутентификация по `apiKey` для создания домена проходит через `ApprovedAccessDomainService.createApprovedAccessDomain`, а через резолвер без `currentUser` отвергается. | В `ApprovedAccessDomainResolver.createApprovedAccessDomain` добавлена проверка `currentUser` и синхронный захват `auditIdentity`, а в `test-research.md` уточнено разделение проверок для `apiKey`. |
| D7 | `minor` | В синтетических тестовых схемах (`crm-audit-application-authorization-and-variable.postgres-spec.ts`) отсутствуют таблицы `core."user"`, `core."apiKey"`, `core."publicDomain"` и колонка `core.workspace."customDomain"`, а в `approved-access-domain.spec.ts` нет `DataSource`. | Все обращения к опциональным таблицам и колонкам защищены через `to_regclass(...) IS NOT NULL` и `to_jsonb(...)->>'...'`; в `runAuditedApplicationDelete` пост-проверка после `audit.flush()` проверяет обе таблицы (`hasAuthTable` и `hasPublicDomainTable`); в сервисах сохранён `@Optional() @InjectDataSource()` fallback для unit-тестов без `DataSource`. |
| D8 | `minor` | В `test-research.md` примеры `redactedDiff.values` были записаны сокращённо без обёртки `{ before, after }`. | Примеры в `test-research.md` приведены в точное соответствие с форматом `CrmAuditTransactionContext` (`{ before, after }`). |
| D9 | `minor` | При чтении строки через `RETURNING to_jsonb(...) AS row` поля `createdAt` и `updatedAt` возвращаются строками, тогда как DTO и Entity ожидают `Date`. | В `workspace-domain-audit.ts` добавлена гидратация `createdAt: new Date(String(row.createdAt))` и `updatedAt: new Date(String(row.updatedAt))`. |
| D10 | `minor` | В `PublicDomainResolver.checkPublicDomainValidRecords` и `PublicDomainService.findByDomain` входной `domain` не нормализовался через `domain.trim().toLowerCase()`. | Добавлена нормализация `domain.trim().toLowerCase()` во всех точках входа `PublicDomainResolver` и `PublicDomainService`. |
