   - Проверяет модульное поведение `ApprovedAccessDomainService` (`createApprovedAccessDomain`, `deleteApprovedAccessDomain`, `sendApprovedAccessDomainValidationEmail`, `validateApprovedAccessDomain`) на моках репозиториев без `DataSource`.
   - При `@Optional() @InjectDataSource()` в `ApprovedAccessDomainService` и отсутствии явного/ambient `auditIdentity` сохраняется обратная совместимость со всеми существующими модульными тестами.

   - Проверяет транзакционный аудит `applicationAuthorization`, `userApplicationVariableValue` и `ApplicationService.delete` (`runAuditedApplicationDelete`) на реальной PostgreSQL БД.

## 2. Новые интеграционные тесты PostgreSQL (`crm-audit-workspace-domain.postgres-spec.ts`)

Создать `packages/twenty-server/test/fork-migration/crm-audit-workspace-domain.postgres-spec.ts`, проверяющий на реальной PostgreSQL БД с непривилегированной ролью `NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT`:

1. **Полный жизненный цикл `approvedAccessDomain` (`create`, `update` при `validateApprovedAccessDomain`, `delete`) через сервис и резолвер**:
   - `ApprovedAccessDomainResolver.createApprovedAccessDomain` (пользовательская сессия, сессия под имперсонацией с разрешением `initiator`, OAuth-клиент `withUser`) и `ApprovedAccessDomainService.createApprovedAccessDomain` (включая `apiKey`) атомарно создают строку `core."approvedAccessDomain"` и запись `crm_audit."crmAuditEntry"` (`action: 'create'`, `redactedDiff: { changedFields: ['domain', 'isValidated'], values: { isValidated: { before: null, after: false } } }`), при этом строка домена никогда не попадает в открытом виде в `crm_audit."crmAuditEntry"`.
   - Захват атрибуции происходит синхронно до первого `await` (`workspaceOrmManager.executeInWorkspaceContext` / `sendApprovedAccessDomainValidationEmail`).
   - При ошибке `sendApprovedAccessDomainValidationEmail` (например, несовпадение домена email или сбой отправки) транзакция полностью откатывает и строку `core."approvedAccessDomain"`, и запись `crm_audit."crmAuditEntry"`.
   - `ApprovedAccessDomainResolver.validateApprovedAccessDomain` и `ApprovedAccessDomainService.validateApprovedAccessDomain` записывают `approvedAccessDomain` (`update`, `redactedDiff: { changedFields: ['isValidated'], values: { isValidated: { before: false, after: true } } }`), отвергают кросс-воркспейсный вызов (`workspaceId` резолвера != `payload.workspaceId`) и повторную валидацию.
   - `ApprovedAccessDomainResolver.deleteApprovedAccessDomain` и `ApprovedAccessDomainService.deleteApprovedAccessDomain` записывают `approvedAccessDomain` (`delete`, `redactedDiff: { changedFields: ['domain', 'isValidated'], values: { isValidated: { before: true, after: null } } }`).
2. **Полный жизненный цикл `publicDomain` (`create`, `update` при `checkPublicDomainValidRecords`, `delete`) и каскадное удаление при `ApplicationService.delete`**:
   - `PublicDomainResolver.createPublicDomain` и `PublicDomainService.createPublicDomain` записывают `publicDomain` (`create`, `redactedDiff: { changedFields: ['applicationId', 'domain', 'isValidated'], values: { applicationId: { before: null, after: applicationId }, isValidated: { before: null, after: false } } }`), отвергают глобальные дубликаты `domain` из других рабочих пространств и `customDomain` рабочего пространства без вызова `deleteHostnameSilently` по чужому домену.
   - `PublicDomainResolver.checkPublicDomainValidRecords` (включая `application` / `oauthClient` субъекты), `CheckPublicDomainsValidRecordsCronJob.handle` (`actor: { kind: 'system', id: 'CheckPublicDomainsValidRecordsCronJob' }`) и `DnsCloudflareService.checkHostname` (`actor: { kind: 'system', id: 'DnsCloudflareService.checkHostname' }`) записывают `publicDomain` (`update`, `redactedDiff: { changedFields: ['isValidated'], values: { isValidated: { before: false, after: true } } }`) по актуальному состоянию строки в БД (`FOR UPDATE`) только при фактическом изменении `isValidated` и не создают пустых записей аудита при неизменном `isValidated`.
   - `PublicDomainResolver.deletePublicDomain` и `PublicDomainService.deletePublicDomain` записывают `publicDomain` (`delete`) и вызывают `dnsManagerService.deleteHostnameSilently` только после успешного удаления строки своего рабочего пространства (не удаляя чужой домен другого рабочего пространства).
   - `ApplicationService.delete` каскадно удаляет связанные строки `core."publicDomain"` (включая случай, когда `core.application."primaryPublicDomainId"` ссылается на удаляемый домен) и `core."applicationAuthorization"` в одной транзакции и записывает атомарные события `publicDomain` (`delete`) и `applicationAuthorization` (`delete`) с общим `operationId` и `correlationId`.
3. **Откат при сбое аудита, защита от повреждения триггером после `flush()`, запрет повторного использования запроса и классификация `NativeTransactionOutcomeUnknownError`**:
   - При отзыве привилегии `INSERT` на `crm_audit."crmAuditEntry"` все операции (`createApprovedAccessDomain`, `validateApprovedAccessDomain`, `deleteApprovedAccessDomain`, `createPublicDomain`, `checkPublicDomainValidRecords`, `deletePublicDomain`, `ApplicationService.delete`) полностью откатывают изменения в `core."approvedAccessDomain"`, `core."publicDomain"` и `core.application`, не отправляют письмо подтверждения и компенсируют регистрацию в `DnsManagerService` (`deleteHostnameSilently`).
   - Триггер `AFTER INSERT ON crm_audit."crmAuditEntry"`, пытающийся модифицировать `core."approvedAccessDomain"` или `core."publicDomain"` после `audit.flush()`, обнаруживается финальной сверкой состояния и откатывает транзакцию.
   - Повторное использование одного объекта `WorkspaceDomainAuditRequest` отвергается.
   - Сбой чтения `COMMIT` (`NativeTransactionOutcomeUnknownError`) классифицируется корректно и не вызывает компенсирующего удаления `deleteHostnameSilently` для возможно зафиксированного публичного домена.
