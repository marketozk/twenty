# Принятая база Twenty 2.52 и состав переиспользования

Дата: 26.10.2026. Основание: просьба пользователя «Возьми из версии 2.52 все что нам понадобится».

## Решение и фактически выполненное

Для разработки принимаем **полный снимок upstream `729f6236126eddaa68d176fb766bc349b19de11d`**, версия исходников `2.52.0`. Он уже является предком нашей рабочей ветки `codex/omnichannel-requirements` и уже целиком находится в `packages/`. Повторное копирование или cherry-pick тех же изменений не требуется. Состав зафиксирован в [машиночитаемом перечне](upstream-2.52.json); это перечень базы и нужных изменений, не конфигурация запуска.

Сравнение с `twenty/v2.51.0` (`15e4826d3b5fc5867baeabeeb42b253892b2d4da`): 74 коммита, 1297 изменённых файлов, 39400 добавленных и 59019 удалённых строк. SHA фиксирует исследованный снимок; плавающий `main` не считается той же версией.

Рассмотрены два способа:

- **Использовать целый существующий снимок — принято.** Все нужные исправления, shared types, lockfile, SDK/CLI и upgrade-команды остаются согласованными. Новых изменений runtime-кода для принятия этой базы: 0.
- Переносить выбранные исправления на 2.51. Это отдельный backport: один только Inbox затрагивает 51 frontend-файл, workflow меняет front/server/shared, participant matching меняет payload очереди. Он добавляет сопровождение и проверку комбинации, которой нет в upstream. Для нашего уже созданного форка необходимости в нём не найдено.

Это выбор исходной базы, **не утверждение готовности интеграции**. В работающем демо установлен официальный 2.51.0 — [проверенный выкат](../twenty_upgrade_2_51/report.md). На момент проверки [последний опубликованный релиз](https://github.com/twentyhq/twenty/releases/tag/twenty/v2.51.0) — 2.51.0; выбранный код 2.52 является снимком разработки.

## Уже готовая основа из 2.51, сохранённая в 2.52

Существенное дополнение к первому исследованию: `modules/messaging` содержит не только email pipeline. Есть **APP message channels** и API `ingestMessages` для внешней переписки. SDK и серверная реализация этих API между 2.51 и выбранным 2.52 не изменились.

Опорные файлы:

- [Документация messaging channels](../../packages/twenty-docs/developers/extend/apps/logic/messaging-channels.mdx).
- [ApplicationMessageChannelsService](../../packages/twenty-server/src/engine/metadata-modules/message-channel/services/application-message-channels.service.ts): владение каналом, видимость, lifecycle.
- [ApplicationMessageIngestionService](../../packages/twenty-server/src/engine/metadata-modules/message-channel/services/application-message-ingestion.service.ts): `ingest`, `toMessageWithParticipants`, проверка идентичностей, блокировка канала, вызов транзакционного сохранения.
- [Входной DTO](../../packages/twenty-server/src/engine/metadata-modules/message-channel/dtos/ingest-app-messages.input.ts): размеры пакета и полей, авторы, внешние ID, даты.

Переиспользуем как основу приёма/импорта: каналы приложения, текст, исходную дату, участников, связь с Person/WorkspaceMember, поток и дедупликацию по `externalId` внутри канала. Если ID провайдера уникален только внутри диалога, адаптер обязан включить идентификатор диалога в `externalId`. Пакет — до 100 сообщений; DTO ограничивает `text` через `MaxLength(262144)` (лимит длины строки, хотя документация обозначает его как 256 KB).

Повторная загрузка не редактирует текст старого сообщения. Позднее уточнение связи участника поддерживается, очистка identity через null — нет. При отключении канала для сохранения истории используется `isSyncEnabled: false`; удаление канала удаляет его сообщения. Это нужно учитывать при отключении юзербота.

**Границы готового API:** исходящая доставка в Telegram/MAX отсутствует; `toMessageWithParticipants` задаёт `attachments: []`. Приём текста не равен поддержке вложений, редактирования/удаления сообщений, delivery/read receipts или автоответов. Внутренний AI Inbox и `Message/MessageThread` — разные модели: готовой связи между общим операторским Inbox и APP ingestion не найдено.

Также уже были в 2.51: пользователи, роли, shared AI threads, участники, assignee, read/archive/snooze, SSE; providers/models/agents/tools; HTTP, code, AI и условия workflow. Их сохраняем и расширяем по требованиям, не считаем новыми функциями 2.52.

## Что не считать готовым

- UI `AiChatApprovalReviewDeck` (`36e47a4b`) и часть новых полей деталей Inbox имеют только controlled props/Storybook, без подключённого runtime lifecycle. Наличие компонентов не означает работающие массовые действия ИИ, ярлыки и статусы.
- Draft-агент после `13de9e02` получает отдельный ID, **но сохраняет общую с live роль**. Изменение существующей роли не изолировано этим исправлением.
- `8fd4b96d` не закрывает group labels по restricted subject/title и возможные выводы через фильтрацию/сортировку. Перед обещанием приватности менеджерам нужны отдельные отрицательные проверки этих путей.
- Enterprise RLS и validation rules уже были в 2.51, не становятся бесплатными от принятия 2.52. Вопрос редакции/реализации прав остаётся открытым.
- Нет готового Twenty-коннектора наших юзерботов, операторского внешнего send, полномочий на конкретные фирмы робота, безопасного режима импорта без автоответов и механизма переключения с SaleBot.

## Проверка принятой базы

Выполнено: проверка достижимости базовых SHA и всех 14 выбранных коммитов; сравнение исходников приложения и файлов зависимостей с выбранным upstream; проверка существования опорных файлов и перечисленных ниже тестов; `git diff --check`. Повторного копирования кода нет, выбранная база уже содержится в форке целиком.

**Unit/integration/build этого снимка ещё не запускались.** Локальный Node — 22.22.0, в проекте требуется `^24.5.0`; node_modules отсутствует, установленного WSL-дистрибутива не обнаружено. Проверка Git подтверждает состав исходников, но не заменяет квалификацию работающей сборки.

До запуска нашей сборки на копии данных нужны проверки:

| Область | Существующая опора и необходимый сценарий |
|---|---|
| Приём и история | `app-message-channels.integration-spec.ts`, `person-participant-rematch.integration-spec.ts`: повторы, исходные даты, чужой канал, отсутствие автора, поздний identity, изменение email. |
| AI context | `ask-ai-application-token-tools.integration-spec.ts`: разрешённый application token и отказ чужой роли/отозванному участнику. |
| Workflow | `core-workflow-draft-step-resources.integration-spec.ts`, `code-step-prebuilt-workflow.integration-spec.ts`; unit `buildTriggerSettingsWithInputSchema`, `resolvePersistedStepOutputSchema`, `shouldSuggestTestingStep`, `generateFormOutputSchema`, `search-variable-in-output-schema.form`. |
| Права/сессии | Messaging/calendar visibility suites, `is-impersonating.util.spec.ts`, `ApolloFactory.test.ts`, successful/failing session creation; добавить проверку гонки superseded и отмеченных groupBy/filter границ. |
| Экран менеджера | `AiChatThreadDetailsDropdown.test.tsx`, sharing tests, renderer properties/sandbox, metadata store consistency/IndexedDB и `delete-object-metadata-view-events.integration-spec.ts`. |

Server и worker должны использовать один образ: `bc3096f1` меняет payload participant-matching jobs, поэтому смешанные версии и сохранённые задания требуют проверки. Полная сборка также включает команды upgrade 2.52; нужен пробный переход на восстановленной копии БД/файлов, `upgrade:status` и проверка очереди. Одного HTTP health недостаточно.

Следующий этап проекта — Design интеграции с учётом APP ingestion и общего Inbox. Принятие базы не выбирает автоматически схему хранения диалогов, место исполнения юзерботов, редакцию доступа или дату переключения клиентов.
