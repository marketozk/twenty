## Продуктовые вопросы

| ID | Что уточнить | Почему важно |
|---|---|---|
| Q-01 | Нужны ли дополнительно внешние группы Telegram/MAX? | Совместная работа нескольких менеджеров в одном клиентском диалоге CRM уже подтверждена. Внешняя группа мессенджера — отдельная возможность; не считать её автоматически выбранной. |
| Q-02 | Нужны ли впоследствии отдельные бот-аккаунты через Bot API? | Основной сценарий — наши юзерботы. Пользователь попросил объяснить термин, а не подтвердил новую интеграцию. Этот вопрос не блокирует исследование текущего сценария. |
| Q-03 | Вход/QR/переподключение аккаунтов должны происходить в интерфейсе Twenty или допустима внешняя панель? | Встроенное управление подключением не обязательно означает исполнение юзербота в процессе Twenty. Эти решения нужно разделить. |
| Q-04 | Какую историю переносить: аккаунты, диалоги, период, сообщения и вложения; что делать с недоступными файлами? | Возможность импорта подтверждена, но объём и критерии полноты пока нет. |
| Q-05 | Каковы правила выполнения каждого инструмента ИИ? | Максимальные прикладные полномочия подтверждены, включая действия. Исследованием составить перечень реальных операций и затем уточнить условия авторизации, подтверждения, выполнения и остановки. Не возвращать объём к режиму «только чтение». |
| Q-06 | Для каких диалогов/ситуаций ИИ отвечает сам и когда зовёт человека? | Автоответ входит в проект, но правила его включения, остановки и эскалации ещё не установлены. |
| Q-07 | Число операторов, аккаунтов, диалогов, сообщений в день; срок хранения и ограничения на файлы? | Определяет нагрузку, поиск, хранение и критерии производительности. |
| Q-08 | Нужны ли дополнительные функции SaleBot для общения: шаблоны, рассылки, отложенные сообщения, команды, существующие воронки? | Полную замену надо проверить по инвентаризации фактического использования. Нельзя молча объявить всё покрытым только экраном чатов. |
| Q-09 | Как распределяются клиенты и доступ между менеджерами/командами? | Отдельные входы, разные права и совместное участие уже нужны. Требуется уточнить правила назначения, добавления коллеги и видимость руководителя; технически проверить их применение по всей цепочке данных. |
| Q-10 — закрыт | Без подписки Twenty; собственная реализация нужных функций. | Для record-level прав и аудита делаем независимые механизмы с проверкой всех путей доступа. Разработка ещё не выполнена. |

## Технические решения после исследования

Готовые механизмы и зависимости описаны в исследовании. Design должен выбрать вариант и закрыть оставшиеся проверки, не объявляя прочитанный код прошедшей live-приёмкой. Единственный экземпляр обновлён нашим снимком 2.52; native UI выбран, карта интеграции APP storage составлена. Интеграция с тендерным роботом исключена из проекта; прежний профильный отчёт не задаёт открытых задач.

1. Какие модели переписки, inbox, CRM-связи, права, очереди, файлы и механизмы ИИ уже есть в выбранной версии Twenty.
2. Для выбранного модуля форка определить file-level изменения persistence/events/access/tools и проверить регрессии; SDK используется только там, где подходит контракт.
3. Что можно переиспользовать из существующих юзерботов/коннектора; какие зависимости от SaleBot требуется убрать.
4. Каноническая история выбрана в Message/MessageThread; реализовать постоянные transaction tests и уточнённую карту identity/receipts из plan/implementation-spec.md.
5. Как предоставить ИИ только разрешённые CRM-данные и остановить устаревшую отправку при вмешательстве оператора.
6. Как переходить с SaleBot: миграция, тестовый маршрут, финальное переключение, доказательство единственного отправителя и откат.

Не предлагать пользователю выбирать техническую архитектуру до проверки возможностей кода. Выводы сопровождаются конкретными файлами и контрактами.

## Уточнения для реализации после кроссревью

Единый актуальный перечень — [implementation-spec, раздел 13](plan/implementation-spec.md#13-единый-реестр-решений-и-gates), G01–G20. Он включает роли/воронки, аккаунты, onboarding, AI/provider/knowledge/budget, externalHumanReplyPolicy, managerReplyPolicy, burst, очередь/минимальную Person projection, custodian, import/retention, нагрузку, backup/recovery, размещение транспорта и backup owner, изоляцию тестов, операционное разделение ролей БД, внешние интеграции, служебные уведомления и dependency preflight. Это условия соответствующей активации, не выдуманные значения. D-18 о собственной реализации без подписки сохраняется; G18 не предлагает покупку.

Уточнение G07 после R7: выбирается общий набор responders (agent/workflow) и customer-visible reply budget на root admission. Конкретное значение не назначено автором; до его выбора совместная отправляющая конфигурация не активируется. Техническая модель этой настройки уже внесена в [design/09](design/09-automation-contract.md), текущий verdict — [STATUS](STATUS.md).

G19 уточняет подпись менеджера клиенту; пока подпись не включена. G12 включает access reconciliation после restore, не только возврат сообщений.

G20 — explicit route auto-reopen; пока не включён, closed сохраняется, новые сообщения видны менеджерам без автоматической отправки.

G04 включает решение о допустимом раскрытии CRM-данных в общей клиентской переписке: readers видят уже отправленный текст. До auto выбрать output scope/читателей по spec §15.23.

G11/G13 включают инвентаризацию сторонних отправителей/owners на выбранных аккаунтах и externalServiceReplyPolicy. Она не приравнивается к externalHumanReplyPolicy: источник подтверждается журналом; до выбора policy — pause/handoff, активация неквалифицированного аккаунта запрещена. «Один sender» — один CRM-dispatch owner/generation. Никаких работ с тендерным роботом из этого не следует.

G12: при отсутствии достоверной внешней access history после restore выбран default deny и аудируемый повторный grant recovery-admin; автоматическое восстановление прав не обещано.
