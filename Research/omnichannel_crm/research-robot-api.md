## 2. Подтверждённая цепочка данных и личности

```text
Клиентская ссылка / токен ЛК
  → lk_api.auth.resolve_token
  → Airtable «Клиенты»: token → uuid
  → MySQL managers JOIN firms: uuid + is_active → фирмы/ИНН
  → серверный профиль {uuid, firms, inns}
  → запросы закупок / SSE / действия от имени этого клиента
```

Факты:

- `R/lk_api/auth.py:14,44–80::resolve_token` использует Airtable для определения клиента и `db.get_client_firms(uuid)` для списка фирм. `R/lk_api/db.py:59–78` выбирает активные связи `managers.uuid → firm_id → firms.inn`.
- `R/lk_api/app.py:51::require_session` использует server-side session и при необходимости токен конкретной вкладки `X-LK-Token` / `?token=`. `session.py:22` создаёт непрозрачный случайный session id. Публичный профиль формируется whitelist-функцией `auth.public_profile`; служебный uuid не предназначен для браузера.
- Название `manager_uuid` здесь означает личность/лицензию клиента робота, от имени которой заряжались закупки. Это **не готовое соответствие сотруднику Twenty**, его роли или команде.
- `R/lk_api/tenders.py:258::manager_clause` и `:297::list_tenders`: доступ ограничен фирмами **и** собственным `manager_uuid`; старые строки с NULL/пустым uuid включаются. Пустой список фирм даёт пустой результат. Но отсутствие uuid в самом helper означает отсутствие менеджерского сужения — будущий интеграционный вызов не должен подставлять пустой uuid как «все разрешённые».
- `R/lk_api/auth.py:49–55` при недоступности Airtable/БД возвращает stale-профиль; `app.py:25–42` при сбое перепроверки сохраняет текущую сессию. Это действующая политика доступности ЛК, а не гарантия немедленного отзыва прав.
- `R/lk_api/results.py:23–46` считает финансовые итоги из Airtable по фирмам, **без разреза по менеджеру**; график статусов `:51–65` дополнительно ограничивается менеджером. Нельзя переносить обещание строгой менеджерской изоляции на все поля `/results`.

Готовой цепочки «сотрудник Twenty → разрешённый клиент CRM → подтверждённая личность канала → клиент робота/фирмы» в просмотренных `lk_api`/`lk_frontend` нет. Поиск `Twenty/twenty` в их прикладном коде совпадений не дал. Её контракт остаётся предметом проектирования.

## 4. Прикладные действия и их фактические гарантии

### Зарядка

`charge.validate` берёт uuid из серверного профиля, ИНН основной и резервной фирм проверяет по `profile.inns`, нормализует номер/деньги/проценты. UUID и сформированный `rec_id` не принимаются произвольно из пользовательской формы.

Поток: `charge_flow.handle → charge.submit → POST backend /api/otc-charge → Celery salebot_duo_charge_task → существующие parol.php/index_app.php → base_moris → charge_check`.

- `R/lk_api/charge_flow.py:103–117`: свежая проверка лицензии; при невозможности чтения её ветка **fail-open**, при этом остаётся проверка по сессионному профилю. Это важно для будущих полномочий ИИ и отзыва доступа.
- `:133–148`: обнаружение существующей зарядки зависит от наличия поля `confirm_recharge`; без поля сохранено legacy-поведение. Нельзя считать любую форму универсально защищённой от перезарядки.
- `:169–230`: принятие backend не выдаётся за завершённую зарядку. После `ReadTimeout` запрос мог уйти, запускается наблюдение. Есть `check_id`, этапы, подтверждение новой строки/ошибки и режим `unconfirmed`.
- `B/backend/otc_flask_proxy.py:2575–2626`: идемпотентность по `salebot-duo:{rec_id}:{id_order}` в Redis через SET NX; при ошибке Redis код разрешает продолжить без блокировки. Это не безусловная exactly-once гарантия.
- `B/backend/tasks.py:1892–1969`: redelivery guard по `main-done`, различаются терминальный отказ и успешная основная зарядка с проблемой резерва. Название `salebot_duo_charge_task` само по себе не означает обращение к API SaleBot.

### Отмена

- `R/lk_api/cancel.py:32–64`: проверяет фирму и менеджера, чужая запись → 404, повтор уже выполненной отмены → `already`, ожидающий стоп → `stopping`, конфликт/дедлайн → 409.
- `:71–102` передаёт в backend идентификатор строки, номер закупки, порог дедлайна и автора. `B/backend/otc_flask_proxy.py:1599–1725::purchase_cancel` проверяет общий сервисный секрет и совпадение record_id/номера, выполняет условный UPDATE и readback с учётом `stop_source`, `publish_state`, `send_publ`.
- **Граница доверия:** backend cancellation не сравнивает `cancelled_by.uuid` с владельцем строки как полноценную пользовательскую авторизацию. Проверка пользователя находится в `lk_api`. Нельзя дать ИИ общий backend secret и считать право на конкретного клиента проверенным самим backend.
- `stopping` — передан стоп; подавать пользователю это как уже отозванную заявку неверно. Подача могла начаться; код специально различает состояния.

### Настройки

- `R/lk_api/settings.py:173–254` разрешает `manager`/`manager_firm`, проверяет ИНН, формирует `updated_by=client:<uuid>` на сервере, пишет через отдельный `X-Settings-Secret`. Есть write-through cache и защита от старого чтения после записи.
- `B/backend/client_settings.py:377–441` проверяет реестр ключей, scope, значение, ownership и locks. Роль admin/client определяется из `updated_by`, который доверенный вызывающий сервис передаёт под общим секретом записи. Это не аутентификация сотрудника Twenty.
- Административные scopes `global`/`firm` существуют, но вопрос, какие из них получит ИИ и кто делегирует такие права, ещё не решён. Максимум прикладных возможностей не означает передачу секретов или произвольного `updated_by` в аргументы модели.

## 5. События и надёжность

`R/lk_api/events.py:43::event_visible` пропускает событие записи только для своей фирмы и своего/пустого менеджера; отсутствие `manager_uuid` при заданном scope отклоняется. В исходящий SSE uuid не включается. Служебный `commissions` только сигнализирует перезапрос.

`sse_stream` поддерживает курсор и heartbeat. Это поток для ЛК; здесь не доказана долговечная подписка бизнес-процессов Twenty, не определены retention/replay, порядок нескольких источников и подтверждение обработки CRM. Наличие SSE нельзя объявить готовой интеграционной шиной с гарантированным восстановлением всех событий.

`R/lk_api/app.py:347,354` имеет служебные публикации. `POST /status-changed` проверяет секрет; `/_internal/publish` рассчитан на закрытие внешнего пути конфигурацией прокси. Эти пути не являются разрешением клиенту/ИИ публиковать выдуманные статусы.

## 6. Зависимости от SaleBot вне коннектора

Полное прекращение общения через SaleBot затрагивает уже существующие исходящие уведомления робота:

1. `R/messaging/dispatcher.py:231::send_to_client` отправляет во **все включённые** каналы: pyrogram, salebot, max_userbot, telegram. Это отличается от ответа в конкретный диалог через выбранный аккаунт. Call site рабочего монолита: `R/SNIFFER_BIG_NEW_STAVROPOL_7_SCHRODINGER.py:10620–10621`.
2. `R/messaging/salebot_resolver.py:42` разрешает менеджера через Airtable в SaleBot IDs; `max_userbot_resolver.py` связывает менеджера с MAX. Это уже полезные источники миграции идентичности, но не готовая модель сотрудников/контактов/нескольких аккаунтов Twenty.
3. `B/backend/otc_flask_proxy.py:1731::_purchase_cancel_notify` вызывает `send_salebot_client` по `base_moris.id_sailbot`. `B/backend/notify.py:120` действительно обращается к API SaleBot. Простая замена коннектора не переведёт эти уведомления автоматически.
4. `B/backend/otc_flask_proxy.py:2292::charge_request_client` умеет поиск в Airtable по **SaleBot client_id либо MAX sender ID**, один из двух параметров. Это сервисная ручка под общим секретом, отдающая служебный uuid; универсального подтверждённого соответствия Telegram user ID / account / chat / Twenty person здесь нет.
5. `POST /api/charge-request` (`B/backend/otc_flask_proxy.py:2412`) создаёт карточку «Зарядки» в Airtable; `/api/otc-charge` — следующий отдельный шаг. Эти функции не нужно путать с одним атомарным действием CRM.

Фактические enabled-флаги и маршруты production в этом исследовании не читались. Перечислены подтверждённые пути в коде, а не утверждение, что каждый из них сейчас активен. Полная инвентаризация всех действующих шаблонов/рассылок/автоматизаций SaleBot остаётся отдельным входом для миграционного плана.

## 9. Неизвестное, которое влияет на проектирование

- Кто делегирует сотруднику CRM доступ к клиентской лицензии робота, одной/нескольким фирмам и административным настройкам.
- Как подтверждать связь чат ↔ клиент, если один человек пишет через несколько каналов или от нескольких организаций; какие старые SaleBot/MAX связи пригодны к переносу.
- Какая политика отзыва/stale-доступа требуется для автономного ИИ; текущий ЛК сохраняет доступ при некоторых сбоях источника.
- Должен ли менеджер CRM видеть финансовые итоги всей фирмы при ограничении отдельных закупок.
- Какие действующие robot notification paths, SaleBot-функции и получатели нужно переключить; назначение единственного отправителя при cutover.
- Какие именно настройки/операции разрешены ИИ, как фиксируются инициатор, клиент, диалог, AI run и результат; универсального такого аудита в исследованных API пока нет.
- Production state и версия внешних PHP/API зависимостей должны быть сверены перед реализационным/миграционным решением. Сохранённый manifest и локальные unit-тесты такую сверку не заменяют.
