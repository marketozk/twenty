# Собственный аудит действий — обязательная часть CRM

Уточнение 26.10.2026: [подробный план всего проекта](../plan/implementation-spec.md), особенно раздел 15, задаёт lifecycle, canonical source keys, scoped AI, restore и fork migrations. Схематичные ключи/названия ниже не заменяют эти точные контракты.

Основание: прямое подтверждение пользователя 26.10.2026; без подписки Twenty (D-18). Это целевой контракт, не уже работающая функция. Аудит используется всей CRM, не только экраном чатов. Предлагаемый общий модуль: `packages/twenty-server/src/engine/core-modules/crm-audit/`; UI: `packages/twenty-front/src/modules/crm-audit/`.

## Проверенные точки интеграции

- `engine/core-modules/event-logs/event-logs.service.ts` помечен `@license Enterprise` и зависит от ClickHouse/лицензии; его не используем как production-backend нашего журнала.
- `engine/core-modules/event-logs/emit/event-log-emitter.service.ts` и `ingest/workspace-event-sink.service.ts` уже формируют/доставляют события. Их доступные контракты можно переиспользовать после проверки зависимостей, но наличие события не означает атомарную запись с CRM mutation.
- `engine/workspace-event-emitter/workspace-event-emitter.ts::emitDatabaseBatchEvent` вызывает in-process EventEmitter2. Такой listener не является единственным источником надёжного аудита.
- `engine/twenty-orm/types/workspace-transaction-scope.type.ts` и messaging `saveMessagesWithinTransaction` дают исследуемую точку общей транзакции. Для обычных CRM mutations и core/metadata-изменений отдельно проследить их transaction owners.
- AuthSession schema содержит sign-in/sign-out/session-revoked; удостовериться, что события собираются на серверных call sites. Клиентский track event не доказывает факт успешного входа.

Server-пути выше относительны `packages/twenty-server/src/`. Текущее исследование прочитало код; runtime и fault-injection ещё не запускались.

## Какие действия фиксируем

| Категория | События |
|---|---|
| CRM | Создание, изменение, удаление/восстановление контактов, компаний, сделок, задач; смена этапа; import/export |
| Диалоги | Назначение/смена ответственного, участники, закрытие/открытие, внутренние заметки, переключение режима ИИ и takeover |
| Отправки | Инициирование, принятие connector, подтверждение провайдера, отказ, unknown, отмена; автор-менеджер/ИИ/workflow и commandId |
| ИИ | Run start/finish/error, вызов изменяющего tool, разрешение/отказ, действие и результат; инициатор и policy version |
| Workflow | Запуск/остановка/ошибка, публикация/деактивация/правка, версия процесса, связь с triggering event и дочерними действиями |
| Доступ | Вход/выход/отзыв сессии, административные изменения ролей/прав, отказы критичных операций, выдача приватного файла и экспорт |
| Подключения | Регистрация/отключение/перепривязка, смена route generation, изменение credential version без значения секрета |

Не писать каждое обновление экрана как пользовательское действие. Для массовых операций сохранять summary + результаты отдельных изменённых объектов с общей correlationId. Просмотр журнала и его экспорт тоже аудируются, без рекурсивного «аудит вставки аудита».

## Запись и достоверность

Схема события: eventId, schemaVersion, workspaceId, serverTimestamp, actorType/actorId, initiatingActor, action, entityType/entityId, outcome, reasonCode, changedFields, безопасный before/after diff, correlationId, causationId, command/run/workflow IDs, policyVersion. Auth identity вычисляется сервером; клиент не выбирает actor. Для background jobs инициатор переносится явно и повторно валидируется.

Тексты сообщений, prompts, пароли, cookie, токены, сессии юзерботов, signed URLs, содержимое файлов и скрытые поля не копируются в diff. Для сообщений — ID/направление/тип и outcome. Значения несекретных изменённых полей включаются только по allowlist; иначе сохраняется название поля и факт изменения. Доступ к diff учитывает права полей, а не только право открыть журнал.

Успешная бизнес-мутация и её audit row/outbox записываются в одной DB transaction. Для workspace и core/metadata операций использовать их собственный transaction owner; нельзя притворяться, что запись во второй БД атомарна. Если журнал недоступен, новое критичное изменение/отправка не принимается. После внешнего вызова его результат не откатывается: сохраняется receipt и повторяется только фиксация результата; повтор send ради «починки аудита» запрещён.

Отказ/ошибка записывается после rollback отдельной транзакцией. Если этот канал недоступен, отказ остаётся отказом, срабатывает явный health/alert; отрицательный аудит не объявляется гарантированно сохранённым. Выход/отзыв доступа не блокируется ради сбоя журнала — безопасность имеет приоритет, а потеря аудита явно сигнализируется.

Audit row append-only: нет пользовательских update/delete API; application role не имеет произвольного изменения событий. Удаление по retention выполняет отдельная служебная роль с журналом задания и учётом backup. Это защита от изменения приложением, не обещание защиты от администратора БД. Срок хранения/архивирования нужно выбрать до реальных данных; автоматическую очистку без решения не включать.

## Просмотр

Раздел «Аудит действий»: фильтры время/сотрудник/источник/действие/объект/результат, цепочка инициатор -> workflow/AI -> изменение/отправка. Детали показывают безопасный diff и причину ошибки. Страница объекта — отфильтрованная часть того же журнала, а не второй журнал.

Отдельные permissions `audit.read`, `audit.export`, `audit.manageRetention`. Менеджер видит допустимые события своей области; руководитель — разрешённой команды. Право читать audit не открывает чужие объекты, поля, счётчики и файлы. Для удалённых/переданных объектов хранится security descriptor; доступ сверяется с текущими правами, историческая роль не даёт пожизненного доступа. Специальный административный просмотр удалённых объектов требует явного разрешения.

## Приёмка

Авария на audit insert откатывает CRM change; повтор команды даёт один success-event. Проверить UI/REST/GraphQL/AI/workflow paths, смену роли во время действия, отсутствие секретов в diff, чужой audit/export/count, late receipt после unknown, retention, восстановление backup и неизменяемость для application role. Изменённая сделка и исходящая команда всегда имеют проверяемый инициатор и цепочку событий.
