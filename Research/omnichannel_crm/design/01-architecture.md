# Архитектура CRM с Telegram/MAX — v1

Дата: 26.10.2026. Объём: [требования v0.4](../requirements.md), D-16; тендерный робот исключён. Основание работы — просьба пользователя зафиксировать архитектуру. Ниже выбранная техническая архитектура для последующего плана, а не описание уже реализованной системы. Выбор платного/собственного механизма доступа пока открыт: пользователь запросил объяснение, а не выбрал покупку.

## Структура и границы

Выбран **модуль внутри форка Twenty + изолированный транспорт мессенджеров**. CRM, операторский интерфейс, бизнес-состояние диалога, ИИ и автоматизации принадлежат Twenty. Коннектор и юзерботы отвечают за аккаунты, протоколы, отправку, получение и журнал доставки. База кода — [фиксированный снимок 2.52](../reuse-2.52.md).

Схема уровня контейнеров (целевое устройство, ещё не развёрнуто):

```text
Менеджер / администратор
          |
          v
Twenty Front: Чаты + карточки клиентов + настройки подключений
          | authenticated API / SSE
          v
Twenty Server: Omnichannel module
  |  Access policy / Conversation / Message / Import / Attachments
  |  существующие CRM / AgentRun / tools / Workflow
  |
  +---- PostgreSQL Twenty: CRM + переписка + inbox/outbox + аудит
  +---- защищённое хранилище файлов Twenty
  +---- Twenty Worker + Redis: выполнение заданий / SSE
          |
          | внутренний аутентифицированный API; стабильные command/event ID
          v
Messaging Connector: маршруты + очередь доставки + журнал (свой PostgreSQL)
          |
          +---- Telegram userbot: сессия + локальный журнал ---- Telegram
          +---- MAX userbot: сессия + локальный журнал ---------- MAX

SaleBot ---- только импорт / временный контролируемый переход
```

Разделение PostgreSQL Twenty и транспортного журнала — логическое владение данными, не требование отдельных физических серверов. Версии и размещение фиксируются при подготовке среды; действующие клиентские базы и аккаунты не переиспользуются в тестовом стенде автоматически.

## Размещение кода и ответственности

Все новые пути ниже **предлагаются**; их наличие или реализация не заявляются.

| Компонент | Размещение | Ответственность |
|---|---|---|
| Экран «Чаты» | `packages/twenty-front/src/modules/omnichannel/` | Список диалогов, сообщения, ответ, вложения, назначения, переход к CRM, управление режимом ИИ. Прямых вызовов юзерботов из браузера нет. |
| Серверный модуль | `packages/twenty-server/src/modules/omnichannel/` | Авторизация, доменные команды, приём событий, связь с существующими messaging services, история, аудит, API менеджера/коннектора. |
| Фоновые задания | Jobs/processors того же модуля, выполняются Twenty Worker | Обработка входящих, outbox, импорт, AI orchestration, reconciliation; PostgreSQL хранит состояние, Redis не является единственным журналом. |
| Общие контракты | `packages/twenty-shared/src/omnichannel/` | Версионированные типы событий/команд и состояния. Не передавать ORM entities наружу. |
| Транспорт | Существующие connector/Telegram/MAX проекты; выделяемые части позже в `integrations/messaging/` этого проекта | Адаптировать существующие очереди, idempotency и receipts. Сессии и секреты не переносить в Git; не копировать целиком старый проект. |

Вход/QR/2FA выполняется юзерботом. В Twenty обязательно видны привязка аккаунта и состояние; нужен ли встроенный экран авторизации — открытый UX-вопрос, не повод перемещать процесс юзербота внутрь Node-сервера.

## Что переиспользуем

| Существующий код | Применение / необходимое расширение |
|---|---|
| `Person`, `Company`, `Opportunity`, `Task`, workspace members, roles | Основные CRM-сущности и учётные записи. Существующая карточка клиента не дублируется в коннекторе. |
| `ApplicationMessageChannelsService`, `ApplicationMessageIngestionService` | APP-каналы, нормализация входящих, identity links, владение подключением. Расширить для надёжного доменного события, вложений и edit/delete. |
| `MessagingSaveMessagesAndEnqueueContactCreationService`, `MessagingMessageService.saveMessagesWithinTransaction` | Сохранение Message/MessageThread/participants/associations. Сохранить общий алгоритм, выделить используемую транзакционную часть для атомарной записи omni-данных. Нынешний публичный метод сам открывает транзакцию — атомарность с новым outbox пока не предоставлена. |
| UI Twenty: layout, list, input, message rendering, record panels | Переиспользовать компоненты после проверки их зависимостей. Новый раздел не притворяется существующим AI Inbox. |
| `AgentRunService`, providers/models, skills/tools | Единая интеграция ИИ. Отдельный LLM backend не создаётся. |
| Workflow executor, очередь, подписки, файловое хранилище | События/действия общения и фоновые задания. Потребуются scoped API, импорт без триггеров и защищённая выдача файлов. |
| Connector `Store.enqueue_send`, адаптеры Telegram/MAX | Повторяемая постановка отправок и транспортные receipts; удалить обязательные SaleBot mirror/project/card зависимости из нового пути. |

Внутренние `agentChatThread` остаются моделью исполнения/контекста ИИ. Каноническая клиентская история — `Message/MessageThread`. История ИИ может быть ограниченной производной копией для выполнения, но не вторым редактируемым источником клиентской переписки. Чужие/отозванные данные не попадают в новый контекст; сохранённый старый AI-контекст после смены области доступа не продолжается.

## Права — контракт определён, реализация редакции открыта

Единая проверка должна защищать не только новый API чатов, но и штатные CRM API, relations, поиск, агрегации, экспорт, файлы, подписки, workflow и AI tools. Скрытие элементов UI не является проверкой доступа.

Варианты реализации — официальная лицензия с готовыми record-level rules либо собственная независимо реализованная политика. В проверенном исходнике сервис штатного RLS помечен `@license Enterprise` и проверяет лицензию/entitlement. Автоматически включать его или убирать проверку нельзя считать проектным решением. [Условия self-hosted](https://twenty.com/terms), [LICENSE](../../../LICENSE).

Покупка и вариант реализации не выбраны. До решения и отрицательных тестов нельзя обещать защищённое разделение реальных клиентов между менеджерами. Независимые модули и стенд с синтетическими данными можно проектировать/готовить; реализация сквозной изоляции остаётся обязательным условием клиентского запуска.

## Развёртывание

- Отдельный тестовый Compose-проект, БД, Redis, файлы, application credentials и маршруты. Рабочее демо 2.51 не является тестовой БД миграций.
- Сборка из фиксированного Git SHA, согласованные server/worker/front/SDK, lockfile; Linux-среда и Node из требований снимка. Не смешивать версии серверов и workers.
- Пробная миграция на восстановленной копии, `upgrade:status`, функциональные тесты. Откат версии после миграции включает восстановление состояния, а не только смену образа.
- При переключении аккаунта ровно один активный потребитель бизнес-событий и отправитель команд CRM. Транспортный журнал может продолжать принимать сообщения во время переключения.
- Контроль: задержка входящих/outbox, ошибки и unknown sends, возраст импорта, разрывы подписки, отклонённые запросы. Логи с ID и кодами ошибок без переписок, сессий и токенов.
