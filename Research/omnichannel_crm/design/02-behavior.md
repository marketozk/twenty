# Потоки и отказоустойчивость

Актуальные определения: [индекс владельцев](../plan/contracts/README.md). Этот документ описывает архитектуру/сценарии; точные контракты и schema находятся у указанных владельцев.

Статус: целевые контракты v1; не реализовано. Все операции scoped по workspace/account/conversation; имена новых сущностей определены в [модели](05-models.md).

## Приём

```text
Юзербот -> Connector journal -> Twenty inbox receipt -> ACK
                                 |
                                 v
               worker -> один commit PostgreSQL:
                 Message + participants + OmniMessageLink
                 Conversation revision + DomainEvent
                                 |
                                 v
                   подписки / workflow / AI / карточки
```

ACK означает надёжную запись входящего события, не завершение его отображения. Receipt содержит payload до успешной нормализации. Одинаковый eventId+payload возвращает прежний результат; тот же ID с другим payload — конфликт и карантин, не молчаливое перезаписывание.

Нормализация связывает только подтверждённый platform/account/peer ID с контактом. Имя, username или совпавший display name не являются доказательством одной личности. При неизвестной личности создаётся контакт по согласованному правилу либо диалог ожидает привязки; другой клиент не выбирается предположением.

Уникальность native message ID задаётся провайдером: ключ включает workspace, аккаунт, диалог и message ID. Live и импорт используют один message key. Одно сообщение в разных подключённых аккаунтах не склеивается автоматически. События edit/delete приходят с ревизией/порядком провайдера; при отсутствии доказанного порядка сохраняются для reconciliation, время приёма не считается версией провайдера.

Необходимый патч persistence: новая identity link и доменное событие коммитятся в одной транзакции с Message и участниками. Используется существующая transaction scope messaging pipeline; текущий `ingestMessages` сам по себе этой атомарности для новых omni-сущностей не гарантирует. DB unique constraints + блокировка обработки одной conversation/identity; 60-секундный cache lock upstream без продления не является единственной гарантией дедупликации.

## Ответ менеджера / ИИ / workflow

1. Команда проходит серверную проверку инициатора, workspace, conversation, аккаунта, вложений и ожидаемой версии состояния. Входящий текст не задаёт actor или полномочия.
2. В одном commit сохраняются OutgoingCommand, текст/ссылки на файлы и audit event. Повтор с тем же idempotency key не создаёт вторую отправку; с другим payload возвращается конфликт.
3. Dispatcher проверяет актуальные права/route/generation и automationEpoch для non-human; controlEpoch принятой human Command не сравнивается, фиксирует начало отправки и вызывает connector с неизменным commandId.
4. Connector надёжно принимает команду и возвращает job ID. Это `accepted`, а не `sent`. При потере ответа Twenty повторяет запрос с прежним ID или читает статус; не создаёт новый transport job.
5. Только connector/adapters управляют повтором вызова провайдера. CRM не делает второй независимый retry уже принятой transport-команды.
6. Подтверждение провайдера создаёт/связывает канонический Message с commandId и native ID. Собственное эхо юзербота сверяется с той же командой. Эхо, пришедшее первым, не создаёт второй bubble.

Неподтверждённая отправка остаётся `outcome_unknown`. Если канал не гарантирует дедупликацию или найти отправленное невозможно, автоматическая повторная отправка запрещена; оператор видит неопределённость и может сознательно инициировать новую команду. «Доставлено»/«Прочитано» показываются только по поддерживаемой квитанции.

Текст ожидающего исходящего хранится в OutgoingCommand; после подтверждения каноничен Message. UI использует commandId для перехода pending bubble в Message, а не показывает обе записи. Продолжительность хранения команд и receipts задаётся политикой retention; не удалять до подтверждения/разбора и резервирования.

## ИИ и человек

Режим conversation: `human`, `assist` или `auto`. `assist` создаёт черновик; `auto` вправе отвечать и выполнять разрешённые действия. Максимальные функции ИИ не равны серверному admin. Политика инструментов содержит разрешённые операции и область записей/клиентов; для явно одобренных правил автоответов не требуется ручное подтверждение каждого сообщения.

AI run захватывает automationEpoch, revision контекста, policy version и triggering eventId. Перед каждым изменяющим tool и внешней отправкой проверяет их заново. Контекст = разрешённая история + CRM + база знаний; сообщения/вложения клиентов считаются недоверенными данными, а не командами сменить роль или доступ. Общие CRM tools нельзя оставить обходным маршрутом вокруг политики разговора.

Takeover под блокировкой увеличивает controlEpoch и automationEpoch, ставит `human`, инвалидирует незапущенные автоответы и запрашивает остановку run. Передача второму менеджеру не удаляет первого из истории авторства. Два менеджера могут участвовать; обязательная блокировка диалога одним человеком не вводится. Нужны optimistic concurrency, уведомление о новом ответе коллеги и явное подтверждение отправки на устаревшем состоянии.

**Изменяющие tools:** проверка epoch/policy и CRM mutation с audit выполняются в одной транзакции под общим fence с takeover/отзывом политики. Блокировка удерживается до commit, порядок взятия locks един для всех путей. Если takeover закоммитился первым, устаревшая mutation отклоняется; если mutation первой получила fence и завершилась, она логически предшествует takeover. Проверка перед отдельным запросом с последующим неконтролируемым commit недостаточна. Это относится и к generic AI tools, и к действиям workflow, порождённым диалогом. При потере контекста такой вызов отклоняется. По исходникам владельцы транзакций установлены: workspace scope и core QueryRunner используют одну БД, но требуют явной передачи executor. [Карта реализации](../implementation/integration-map.md) фиксирует точки изменения. Атомарность и конкуренция будущего fence проверяются постоянными тестами при реализации; текущее исследование не означает, что защита уже работает.

**Граница отмены:** пока команда не передана на исполнение, takeover предотвращает отправку. Уже принятый/исполняемый внешним транспортом запрос может завершиться после takeover; отозвать его гарантированно невозможно. UI показывает такие команды; провайдерный cancel применяется только при подтверждённой поддержке. Порядок takeover и начала dispatch определяется одной серверной блокировкой/ревизией, а не временем в браузере.

## Вложения, заметки, события

Внутренняя заметка — отдельная сущность и тип события, она никогда не является outbound payload. Вложение проходит проверку типа/размера, сохранение в защищённое хранилище, связь с разрешённым Message/Command и готовность к доставке. Отображение отсутствующего или недоступного файла явно отличает «не импортирован» от «нет вложения».

Внешний edit/delete сохраняет аудит. Удалённое содержимое убирается из активного поиска/AI-контекста согласно retention; отмена внешней отправки не обещается задним числом. Неподдерживаемый тип не исчезает молча: событие получает понятную причину и доступно reconciliation.

События имеют eventId, causationId, correlationId и origin. Workflow получает live-события после commit; consumer receipt связывает событие с единственным execution ID. Receipt различает pending/running/completed: наличие строки не означает завершение эффекта. Падение между claim и запуском оставляет возобновляемую работу; enqueue в Redis восстанавливается из PostgreSQL. Повторные публикации не означают «exactly once» внешнего эффекта — сами действия также идемпотентны. Служебные изменения, исходящие эхо и заметки не превращаются в новые входящие клиента.

## Импорт и переход

Импорт проходит тем же persistence path с `origin=history_import`, исходным временем и checkpoint. **Не запускает** автоответы, уведомления клиенту и бизнес-workflow, включая стандартные record-created triggers: origin/suppression должен доходить до общего диспетчера событий, одного флага в UI недостаточно. Индексация/связи/обновление прогресса разрешены.

Граница import/live фиксируется cursor/watermark источника, перекрытие допустимо благодаря общей дедупликации. Неполнота источника фиксируется в ImportBatch, завершение означает обработанный доступный диапазон, а не обещание восстановить отсутствующие данные.

Automatic admission определяется [единственной схемой §3](../plan/implementation-spec.md#3-схема--rob-764) и [потоком §5](../plan/implementation-spec.md#5-durable-events-и-importlive). Проверка import-first/live-first/parallel и смены activationVersion должна дать одну canonical Message и не более одного automatic customer admission.

Переключение: тестовый маршрут -> сверка -> блокировка новых исходящих старого владельца -> дренирование/разбор in-flight/unknown -> переключение поколения маршрута -> replay непринятых событий -> проверка единственного отправителя. Старые credentials не должны позволять отправлять в новое поколение маршрута. SaleBot выключается для выбранного маршрута только в отдельно разрешённом переходе; для отката аналогично дренировать/сверить Twenty, не запускать двух отправителей одновременно.

Закрытие диалога также повышает automationEpoch и отменяет pending non-human effects. Closed не допускает новых автоотправок; входящие сохраняются и видны менеджерам. Reopen вручную либо по выбранной G20 policy; старые turns не оживают (spec §15.22).
