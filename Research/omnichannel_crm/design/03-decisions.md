# Архитектурные решения и оставшиеся выборы

Авторская актуализация после R7: [единый контракт автоматизации](09-automation-contract.md) внесён в основной план; независимая проверка ещё требуется. Инструменты/делегирование, stable workflow identity, полный запрет pausing и общая квота ответов определены этим контрактом.

Статус: выбранная рабочая архитектура для технического плана по запросу пользователя; runtime не изменён. Не приписывать пользователю выбор платной лицензии или деталей, на которые он ещё не ответил.

## ADR-01. Модуль внутри форка, транспорт отдельно

Варианты:

1. Только SDK app: меньше зависимости от ядра, но нет доказанного subscription-клиента, fetch bridge буферизует SSE; не решены общие права, persistence и связь внешних сообщений с UI.
2. **Модуль Twenty + существующие транспортные адаптеры — выбран.** Прямой доступ к общим компонентам, транзакциям и серверной авторизации; юзерботы изолированы по процессам/секретам.
3. Отдельная CRM/chat-платформа: быстрее при готовом inbox-продукте, но дублирует UI, пользователей, хранение и интеграцию ИИ; противоречит цели максимального переиспользования Twenty.

Цена выбранного варианта: собственные front/server/shared модули плюс ограниченные изменения persistence, event dispatch, file access, tools и всех путей доступа. Это несколько подсистем, а не один плагин. Точное число изменяемых файлов ещё не установлено; обещания «минимальный патч на 2 файла» нет. Перед реализацией обязателен file-level план и проверка регрессий. APP metadata/connection provider может описываться небольшим приложением, но оно не становится отдельной CRM.

## ADR-02. Каноническая история — существующие Message/MessageThread

Альтернативы: сделать AI threads внешней историей; создать собственную полную таблицу сообщений; использовать существующий messaging storage. Выбран третий вариант: уже есть внешние ID, дата, участники, CRM links и APP ingestion.

AI Inbox предоставляет полезные UI и patterns, но его role/actor/run semantics не подменяют внешнего клиента. Операторское состояние добавляется как Conversation; собственные сообщения/экраны почты сохраняют старое поведение. AI execution history — производный контекст, с правилами сброса при отзыве доступа.

## ADR-03. Одна бизнес-команда, один транспортный владелец повторов

Менеджер, ИИ и workflow вызывают один ConversationCommandService. PostgreSQL outbox сохраняет бизнес-команду; connector journal сохраняет попытки доставки. Эти два журнала имеют разное назначение. Connector владеет provider retry; Twenty повторяет только доставку неизменной команды в connector и проверку статуса. Неизвестный результат не превращается в новую команду автоматически.

## ADR-04. Права проверяются по всем путям

Зафиксирован единый контракт actor/workspace/resource/action и отрицательные тесты. По D-18 выбрана **собственная реализация record-level isolation**, без подписки и без runtime-зависимости от Enterprise RLS. Коммерческий код доступен для development/testing на условиях лицензии; снятие проверки не является независимой реализацией.

Реализовать один механизм и его интеграцию с новым модулем, generic API, search/export/relations, файлами и tools. До реализации protected multi-manager acceptance блокируется; отсутствие механизма не означает доступ по умолчанию. Возможности стандартных бесплатных ролей сверить по контрактам, не считать их заменой record-level isolation. [Состав собственной разработки](07-license-boundary.md).

## ADR-05. Переиспользовать ИИ Twenty с областью разговора

Providers/models, agent execution, skills, tool registry и workflow остаются Twenty. Новый orchestration layer добавляет trusted conversation scope, automationEpoch (отдельно от controlEpoch UI CAS), аудит и единую отправку. Ни app-wide token, ни системный workspace context не дают автоматически полномочия клиента. Prompt не назначает права. Для workflow хранится scoped инициатор; потеря/отзыв scope означает отказ, а не fallback к admin.

Редактирование полномочий черновика должно использовать отдельную версию политики/роли; опубликованный run остаётся на своей версии до публикации. Текущий upstream копирует агенту ту же роль — это отдельная необходимая доработка, а не готовая изоляция. Изменение общих настроек роли вне workflow остаётся самостоятельным административным действием с аудитом.

## ADR-06. Миграция истории не является новым обращением

Импорт и live используют единую нормализацию и message identity. Import origin переносится через общий event dispatch; стандартные automation triggers тоже подавляются. Перенос вложений и edit/delete расширяет текущий текстовый APP API. До отдельного разрешения не выполнять импорт реальной переписки или переключение маршрутов.

## Что ещё требует ответа / исследования

| Вопрос | Что уже зафиксировано | Что остаётся |
|---|---|---|
| Собственные права — выбор закрыт | Без подписки Twenty, собственная политика (D-18) | File-level план реализации и проверка покрытия всех путей |
| Авторизация аккаунтов | Выполняется юзерботом, credentials изолированы | Встроенный QR/login UI или внешняя панель; не блокирует транспортный контракт |
| Роли и команды | manager/lead/admin как исходная схема; deny при отсутствии разрешения | Конкретные назначения, совместный доступ, видимость руководителя |
| Группы / Bot API | Личные диалоги + несколько менеджеров CRM; юзерботы | Внешние группы и отдельные бот-аккаунты не входят в обязательный объём |
| История и файлы | Импорт с checkpoint, отметками неполноты и без автоответов | Аккаунты/период, матрица форматов, размеры, retention и резервирование |
| ИИ | Автоответы и прикладные CRM-действия входят в цель | Модель, бюджет, разрешённые операции/сценарии, база знаний и её ACL |
| Нагрузка | Надёжность важнее неподтверждённого SLA | Число аккаунтов/менеджеров, поток сообщений, целевая задержка |

Эти пункты не заменяются произвольными лимитами и не скрываются как готовые настройки. При изменении решения обновляются ADR и проверки, а не только UI.
