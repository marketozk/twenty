## 3. Фактические цепочки данных

### 3.1. Входящее сообщение

1. Telegram `Runtime.on_message` (`C/telegram-userbot/app/transport.py:265`) принимает только `event.is_private`, исключает служебные чаты и передаёт сообщение в `capture`. MAX `BridgeAdapter.observe` (`M/Userbots-Max/src/bridge_adapter.py:251`) отбрасывает известные группы/каналы/свой чат.
2. Адаптер сохраняет событие в SQLite. У Telegram уникальность `(account_id, chat_id, message_id)` (`app/store.py:20`), у MAX дополнительно учитываются направление и слот пустого/полного содержимого (`bridge_journal.py:38,178`). Журнал и команды переживают перезапуск.
3. `UserbotAdapter.events` (`C/.../userbot.py:258`) читает страницы по курсору, проверяет порядок и принадлежность аккаунту. Для общего MAX-журнала есть отдельный account-scoped контракт. HTTP 410 означает потерю доступного окна журнала, а не пустой успешный ответ (`userbot.py:213`).
4. `normalise_event` (`models.py:46`) сохраняет платформу, аккаунт, чат, ID сообщения, направление, текст и вложения. Опциональное время источника отделено от content hash; профиль не является ключом сообщения.
5. `Store.ingest_batch` (`store.py:782`) в одной транзакции сохраняет события/задания и продвигает курсор. Изменённое содержимое уже принятого source ID попадает в quarantine, а не незаметно перезаписывает сообщение.
6. **Сейчас `Store._ingest` (`store.py:605`) создаёт задания `mirror` и `variables`.** Worker публикует текст/вложения в карточку SaleBot и обновляет переменные; это точка текущей зависимости от SaleBot, а не готовое событие для Twenty.

Таким образом, надёжный приём и транспортная идентичность уже реализованы. Готового клиента Twenty, событийного контракта для его workflow и постоянной истории нового CRM в этом потоке нет.

### 3.2. Ответ оператора и отдельный API отправки

- Обычный действующий путь: webhook SaleBot → парсер/разрешение карточки и маршрута → PG `events/jobs` → worker → адаптер юзербота → Telegram/MAX. Поведение общей карточки может выбирать маршрут последнего входящего/явного переключения; для Twenty необходим собственный явно выбранный маршрут, а не перенос правил карточки без проверки.
- Есть независимый вход `POST /v1/routes/{route_id}/send` (`server.py:334`): `command_id` из `[A-Za-z0-9_-]{1,128}`, текст до 4096 символов, максимум одно вложение, `not_before`, `expires_at`. Ответ HTTP 202: `state=queued`, `delivered=false`, ID задания.
- `Store.enqueue_send` (`store.py:1217`) сохраняет такое событие как источник `admin`. В контракте нет идентификатора сотрудника Twenty, роли ИИ, версии владения диалогом или родительского входящего сообщения. Эти сведения потребуются отдельно для совместной работы и отмены устаревшего ответа.
- Для файлов этот метод повторно использует `parse_webhook` SaleBot; downloader по умолчанию разрешает домены SaleBot (`config.py:112,276`). Поэтому «поменять только URL интерфейса» недостаточно даже при наличии готового send API.
- Worker формирует устойчивый command ID из instance ID коннектора и job key (`worker.py:755`) и вызывает `UserbotAdapter.send`. Успех с platform message ID возвращается как `receipt=api_accepted`, **`delivered=false`** (`userbot.py:544`): подтверждение приёма внешним API не означает доставку на устройство или прочтение.

### 3.3. Надёжность и повторная отправка

- `Store._event` и `_job` (`store.py:480,493`) сопоставляют ID и hash намерения. Повтор с другими байтами отклоняется. Нет дедупликации только по одинаковому тексту.
- `Store.claim` (`store.py:900`) использует PG-транзакции, `SKIP LOCKED`, lease token, упорядочивание и признаки начатого внешнего эффекта. Истёкший lease с начатым эффектом переводится в `outcome_unknown`, а не в обычную очередь.
- `Store.resolve` (`store.py:1268`) требует evidence. Неизвестный SEND не разрешается слепо повторять; отдельная автоматическая проверка через SaleBot history относится к mirror, не является универсальным решением для исходящих Telegram/MAX.
- Telegram `Runtime.send` (`app/transport.py:499`) хранит фиксированный peer и random ID до RPC; после timeout/cancel/неопределённого ответа сохраняется `outcome_unknown`. `Store.recover` (`app/store.py:36`) также сохраняет неопределённость после аварии.
- MAX `BridgeAdapter.send` (`M/.../bridge_adapter.py:316`) сериализует отправку, хранит команду до вызова платформы, возвращает сохранённый результат для завершённых/неизвестных команд. Reconnect до SEND отличается от сбоя после возможной отправки кадра. `BridgeJournal` использует SQLite WAL/FULL и восстанавливает inflight как unknown (`bridge_journal.py:47,88`).

Это полезная уже созданная база. Она не решает конфликт «два менеджера и ИИ одновременно отвечают»: транспорт предотвращает повтор одной команды, но разные валидные команды от разных авторов выполнит как разные сообщения.

## 4. Доступ, подключение аккаунтов и совместная работа

`protected` (`C/.../server.py:81`) различает:

- webhook secret для SaleBot;
- токен конкретного аккаунта для входящих событий;
- ключ партнёра для `/partner/v1/*`;
- общий admin Bearer для остальных `/v1/*`;
- публичную media-ссылку с отдельной подписью и TTL.

Partner API уже проверяет принадлежность аккаунтов и маршрутов партнёру (`partner_api.py:99,356`); чужой объект не выдаётся. Регистрация требует разрешённого destination, адреса/токена адаптера, затем проверяет `/health` и журнал (`partner_api.py:180`). Первое подключение начинает чтение с текущего конца журнала: оно само по себе **не импортирует старую переписку**.

Это разграничение интеграторов, а не сотрудников CRM. В изученном API нет учётных записей менеджеров, команд сотрудников, прав на сделки, ACL вложений по пользователю или владельца AI-ответа. Выдача admin/partner токена в браузер Twenty обошла бы нужную предметную авторизацию; перенос прав должен быть частью будущего серверного контракта.

Вход в мессенджер реализован отдельно:

- Telegram `app/auth.py:24` — CLI-код/QR и при необходимости 2FA, `SessionLock`; runtime проверяет владельца сессии.
- MAX `SessionManager.add_account_interactive` / `add_account_with_qr_callback` (`M/.../session_manager.py:182,214`) — интерактивная авторизация, сохранение аккаунта, состояние reauth_required.
- HTTP Partner API регистрирует уже работающий адаптер. Встроенный в Twenty экран подключения можно исследовать отдельно от процесса исполнения сессий; готового безопасного web-login API QR/2FA эти входы не предоставляют.

Для нескольких менеджеров в одном личном клиентском чате создавать нативную группу не требуется. Telegram/MAX принимают сообщение от подключённого аккаунта; внутреннего автора-менеджера надо хранить в CRM. В текущем normalized event есть `direction`, но нет неизменяемого manager ID. Отправки непосредственно из приложения владельца аккаунта отличаются от сообщений, инициированных через CRM.

**Настоящие группы сейчас намеренно ограничены:** Telegram capture только private; MAX `non_dialog_reason` (`M/.../bridge_adapter.py:135`) исключает группы/каналы, а центральный `UserbotAdapter.send` дополнительно отклоняет MAX group chat (`C/.../userbot.py:521`). Это не препятствует согласованному shared inbox, но если понадобятся внешние групповые чаты, потребуется отдельная модель участников/авторов и изменение контрактов.

`history-attach` (`partner_api.py:467`) переносит **текстовый файл** архива и ссылку на него в карточку SaleBot. Он не создаёт исторические сообщения нового CRM по одному. Повторяемость архива по hash полезна, но не заменяет идемпотентность импортера Twenty.

У архива есть ещё важная семантика: `_reply` (`archive.py:58`) называет accepted SEND строкой `delivered`, хотя runtime `UserbotAdapter.send` явно возвращает `api_accepted`, `delivered=false`. Импорт должен сохранить исходную степень доказанности и не превратить это условное архивное название в подтверждённую доставку/прочтение.

Native backfill Telegram (`app/transport.py:313`, `server.py:204`) пишет события в рабочий журнал. Если использовать его как импорт без разделения режимов, существующий connector обработает их как обычные входящие и создаст mirror/variables. Для целевого импорта обязательно отдельно описать подавление автоматизаций/автоответов, границу live/history и дедупликацию.

Не установлены объём, временной диапазон, фактическая полнота SaleBot/native histories, доступность старых файлов и соответствие ID одного человека между каналами. Прочитанный код не позволяет обещать восстановление удалённых/не захваченных сообщений.

## 6. Файлы и функциональные ограничения сообщений

- Central media pipeline уже проверяет HTTPS host allowlist, размер/hash/MIME, ограничения адресов, скачивает, проверяет ffprobe и загружает в адаптер (`media.py`). Эти проверки — переиспользуемое поведение, а не препятствие для миграции.
- Публичная media-ссылка подписывается на 7 суток (`media.py:302`), доступ определяется possession ссылки, а не текущими правами менеджера. Это не готовая модель долговременных вложений с ACL Twenty.
- Нельзя обещать поддержку всех типов сообщений: MAX `mirror_content` (`models.py:87`) явно помечает неподдержанные контакты, геопозиции, звонки и другие вложения; кнопки/preview могут не переноситься. Проверенные в коде photo/video/file/voice paths не доказывают live-приёмку всех комбинаций.
- Контракт событий не содержит универсальных операций edit/delete/reaction/read-receipt/typing/reply-thread. Изменённое содержимое того же source ID может уйти в quarantine, а не стать редактированием сообщения. Эти возможности требуют отдельного решения по объёму продукта.
- В MAX есть собственные business handlers и старый external send API для робота. В M `external_api.py:284` вызывает `record_external_send` для текста, отправленного вне bridge. Это важная существующая развилка: отключение всего процесса MAX ради CRM может затронуть бизнес-сценарии робота. Рабочий набор таких сценариев/уведомлений ещё нужно инвентаризировать.

## 9. Выход исследования для проектирования

**Переиспользуемая база:** транспортные route/command ID, адаптеры сессий, журналы и квитанции, очереди и lease/fencing, обработка файлов, профили, реестр аккаунтов и Partner API, инструменты чтения истории.

**Требуют адаптации:** текущий SaleBot sink, представление истории и вложений, mapping клиента/карточки, caller/auth contract исходящих, наблюдаемость новой CRM, импорт и интеграция workflow/ИИ.

**В изученном коде не готовы:** интерфейс командного inbox, отдельный автор-менеджер и ACL диалога/вложений, человек/ИИ ownership с отменой устаревшего ответа, сделки/этапы Twenty, нормализованный importer Twenty, безопасный web-login QR/2FA.

Открытые инженерные вопросы: выбранная рабочая ревизия MAX и реальная комбинация production-сервисов; перечень адаптеров владельца/компаньона и права на их изменения; источник полного архива; обязательные типы сообщений; кто владеет финальной историей и квитанциями; как Twenty получает durable события и подтверждает обработку; как не задеть независимые уведомления робота. Эти факты достаточны для сравнения способов интеграции, но не для автоматического переключения живых клиентов.
